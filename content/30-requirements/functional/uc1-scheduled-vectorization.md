## JTBD

Когда в SMP накапливаются новые или изменённые объекты целевых классов (`knowledgeBase`, `problem`, `issue`), и для них ещё нет актуального векторного представления, я (владелец продукта `pg_vector_service`, Демьянов) хочу, чтобы фоновая джоба по расписанию пакетно векторизовала такие объекты через выбранную модель эмбеддинга и сохраняла результат в pgvector-таблицу через SMP API, чтобы последующие сценарии similarity-поиска (UC2) и кластерного анализа (UC3) работали на свежих векторах без ручных операций оператора и без перерасхода квоты Yandex Cloud Foundation Models.

## Описание

Сценарий — фоновая массовая векторизация SMP-объектов: запускается по cron-расписанию, обрабатывает только те объекты, для которых вектор отсутствует или устарел, складывает результат в защищённую pgvector-таблицу через SMP API. Это инфраструктурный сценарий: пользовательского интерфейса у джобы нет, оператор Service Desk не взаимодействует с ней напрямую. Конечная бизнес-ценность раскрывается в UC2 и UC3, но без UC1 они физически не могут работать — данные для них формирует именно эта джоба.

В PoC-итерации старт идёт с PII-нейтральных классов (`knowledgeBase$article`, `knowledgeBase$section`), затем подключается `problem`, в последнюю очередь — `issue` и его подклассы (требует завершённого PII-аудита whitelist'а атрибутов). Композитный текст для эмбеддинга формируется конкатенацией только белого списка текстовых атрибутов конкретного класса; всё, что не входит в whitelist, в YC FM не уходит.

Джоба идемпотентна: повторный запуск на одном и том же состоянии данных не делает повторных платных вызовов YC FM и не перезаписывает уже актуальные векторы. Идемпотентность строится на двух маркерах объекта: «вектор устарел» (`vector_dirty`) и «версия модели эмбеддинга, которой посчитан вектор». Любое изменение объекта по whitelisted-атрибутам и любая смена версии модели — приводят к пересчёту в следующий запуск джобы.

Сценарий **синхронной** векторизации по событиям SMP (action handler на change/create) — out of scope этого требования (см. секцию «Что НЕ входит»).

## Что НЕ входит в UC1 (out of scope)

- **Sync-векторизация по событиям SMP** (action handler на create/update/status-change) — отдельный сценарий, в PoC не реализуется.
- **Similarity-поиск** «найди похожие на этот объект» — это UC2.
- **Кластерный анализ / автообъединение дублей** — это UC3.
- **Конкретный выбор модели эмбеддинга, размерности вектора, типа индекса (HNSW vs IVFFlat), метрики расстояния, схемы pgvector-таблицы** — не решается в BA, фиксируется в ADR на этапе `/sa` (см. ссылки в FR/BR).
- **Прямой JDBC-доступ к БД** — архитектурно запрещён (CLAUDE.md, красные линии); используется только SMP API.
- **PII-маскирование / анонимизация текстов** до векторизации — на PoC решается через whitelist (атрибуты с высоким PII-риском в whitelist не попадают). Вопрос автоматической маскировки — открытый, см. секцию «Открытые вопросы».

## Функциональные требования

- **FR-001. Триггер по расписанию.** Джоба запускается планировщиком SMP (`scheduledTask`) по cron-подобному расписанию. Конкретные параметры расписания (период, время старта, стратегия `from_start`/`from_last_execution`) настраиваются администратором стенда без изменения кода модуля. Решение по дефолтному расписанию — закрепится в ADR-YYY (jobs-scheduling).
- **FR-002. Целевые классы.** Джоба обрабатывает SMP-объекты следующих FQN-классов: `knowledgeBase$article`, `knowledgeBase$section`, `problem` (включая `problem$problem`), `issue` и его подклассы (как минимум те, что присутствуют на стенде `llm2`: `issue$issue`, `issue$incident`, `issue$SAP`, `issue$equipmentReq`). Список целевых классов — параметр конфигурации модуля, изменяется без перекомпиляции JAR.
- **FR-003. Очередность подключения классов.** В рамках PoC классы подключаются в порядке роста PII-риска: сперва `knowledgeBase$*`, затем `problem`, затем `issue` и его подклассы. Подключение каждого следующего класса — отдельная управленческая контрольная точка (gate) с подтверждением от owner'а, что PII-аудит whitelist'а пройден.
- **FR-004. Whitelist атрибутов.** Для каждого целевого класса джоба векторизует **только** атрибуты из явного whitelist'а (см. BR-001). Любой атрибут, не входящий в whitelist, в текст для эмбеддинга **не попадает**.
- **FR-005. Композитный текст.** Текст одного объекта для эмбеддинга формируется конкатенацией значений whitelisted-атрибутов в фиксированном порядке (порядок — параметр конфигурации класса). Пустые/null-значения пропускаются. Решение по разделителю и нормализации richtext (HTML → plain) — закрепится в ADR-YYY (text-normalization).
- **FR-006. Чанкинг длинных текстов.** Если итоговый композитный текст превышает лимит модели эмбеддинга по токенам, он разбивается на чанки с overlap'ом. Решение по способу склейки эмбеддингов чанков (один вектор на объект через усреднение / max-pooling vs хранение нескольких векторов на объект) — закрепится в ADR-YYY (chunk-aggregation).
- **FR-007. Маркер `vector_dirty`.** Каждый целевой объект имеет признак, по которому джоба определяет, требуется ли пересчёт вектора. Признак выставляется в «требуется пересчёт» в момент изменения любого whitelisted-атрибута объекта. Способ реализации (отдельный атрибут SMP / mtime-сравнение / выделенная staging-таблица) — закрепится в ADR-YYY (dirty-tracking).
- **FR-008. Идемпотентность.** Если повторный запуск джобы выполняется на состоянии данных, в котором ни у одного объекта `vector_dirty` не установлен и версия модели эмбеддинга не менялась, джоба **не делает ни одного платного вызова YC FM** и завершается с информационной записью в лог.
- **FR-009. Версионирование модели эмбеддинга.** Имя и версия модели эмбеддинга, которой посчитан вектор, сохраняются вместе с вектором (или ссылкой на конфигурацию). При смене модели или её размерности — все векторы помечаются как требующие пересчёта; конкретные шаги миграции (single-pass пересчёт vs blue-green) — закрепятся в ADR-YYY (model-versioning + migration-runbook).
- **FR-010. Сохранение через SMP API.** Запись вектора и метаданных (id объекта, FQN, версия модели, timestamp) выполняется **только** через SMP API (REST `/edit`, `/create` или скрипт-метод модуля). Прямые JDBC-вызовы — запрещены архитектурно (CLAUDE.md).
- **FR-011. Пакетная обработка.** Джоба обрабатывает объекты батчами фиксированного размера. Размер батча — параметр конфигурации модуля. Решение по дефолтному размеру батча — закрепится в ADR-YYY (batch-size).
- **FR-012. Обработка ошибок YC FM (rate limit / timeout).** При получении HTTP 429 (rate limit) или таймаута сетевого вызова джоба применяет retry с экспоненциальной задержкой; при исчерпании числа ретраев — объект помечается как «не векторизован, причина: rate-limit/timeout», `vector_dirty` остаётся установленным (объект попадёт в следующий запуск). Конкретное число ретраев и backoff-параметры — в ADR-YYY (yc-fm-retry-policy).
- **FR-013. Обработка deprecated/недоступной модели.** Если YC FM возвращает ошибку «модель недоступна / deprecated» (или эквивалент), джоба прерывается с записью критической ошибки в лог и единственным алертом owner'у; объекты не помечаются как «провалившиеся» (не наказываем данные за инфра-инцидент).
- **FR-014. Логирование прогресса и ошибок.** Джоба пишет в лог SMP: время старта, число обработанных/пропущенных/упавших объектов в каждом батче, итог запуска, любые ошибки YC FM с `correlationId`. Stack traces — только в лог, не в исходящие сообщения. Конкретный формат структурированного лога — закрепится в ADR-YYY (logging-format).
- **FR-015. Защита от наложения запусков.** Если предыдущий запуск джобы ещё не завершился, новый запуск по расписанию **не стартует** (детектируется по lock'у или статусу `scheduledTask`). Решение по реализации lock'а — закрепится в ADR-YYY (job-locking).
- **FR-016. Граница допустимого окна работы.** Джоба либо завершает обработку всех «грязных» объектов, либо мягко останавливается по достижении максимального времени работы (cap), не оставляя БД в несогласованном состоянии. Конкретный cap (минут / часов) — закрепится в ADR-YYY (job-time-budget); как открытый вопрос на старте PoC — без cap'а.

## Нефункциональные требования (специфичные для UC1)

> Общие NFR (безопасность, наблюдаемость, тестируемость) — в отдельном артефакте `content/30-requirements/non-functional/`. Здесь только то, что специфично именно для джобы.

- **NFR-UC1-001. PII-фильтрация на входе модели.** В YC FM не должен уходить ни один атрибут SMP-объекта, который не входит в whitelist (BR-001). Это инвариант, проверяемый автоматически (см. AC-008).
- **NFR-UC1-002. Бюджет YC FM.** Расход токенов YC FM на разовый full-rescan всех целевых объектов одного тенанта — в пределах согласованного бюджета. Конкретные цифры (₽ / токенов / объектов) — открытый вопрос (см. секцию «Открытые вопросы»), фиксируются после RES-003.
- **NFR-UC1-003. Влияние на стенд.** Джоба не должна заметно деградировать отклик SMP для операторов в часы её работы. «Заметно» — открытый вопрос (требует целевой метрики от owner'а / DevOps).
- **NFR-UC1-004. Целостность данных.** Если запись вектора в pgvector прервалась посередине батча (сбой SMP, network-fail), состояние объекта в SMP остаётся в одном из двух валидных состояний: либо «вектор не сохранён, `vector_dirty` = true», либо «вектор сохранён, `vector_dirty` = false, версия модели зафиксирована». Промежуточное состояние («вектор сохранён, но без версии модели») — недопустимо.

## User Journey

Действующее лицо — **планировщик SMP** (а не человек). Owner / DevOps выступают наблюдателями.

1. **Триггер.** Планировщик SMP по расписанию (FR-001) запускает скрипт `scheduledTask` модуля `pg_vector_service`.
2. **Pre-flight.** Джоба проверяет: (а) lock не занят (FR-015); (б) текущая версия модели эмбеддинга прочитана из конфигурации; (в) доступ к pgvector-таблице через SMP API живой; (г) IAM-токен YC FM свежий или обновлён.
3. **Выбор кандидатов.** Джоба запрашивает через SMP API список объектов целевых классов (FR-002), у которых либо `vector_dirty` = true, либо версия модели в записи вектора не совпадает с текущей (FR-009). Выборка пагинируется (FR-011).
4. **Обработка батча.**
    1. Для каждого объекта формируется композитный текст из whitelisted-атрибутов (FR-004, FR-005).
    2. Текст чанкуется при необходимости (FR-006).
    3. Вызов YC FM на эмбеддинг текста (или чанков).
    4. Агрегация эмбеддингов чанков в один вектор (стратегия по ADR-YYY chunk-aggregation).
    5. Запись вектора + метаданных (id, FQN, версия модели, timestamp) в pgvector через SMP API (FR-010).
    6. Сброс `vector_dirty` = false (FR-007) — атомарно с записью вектора (NFR-UC1-004).
5. **Альтернативный путь A. Rate limit / timeout YC FM.** FR-012: retry с backoff, при исчерпании — объект остаётся «грязным», переходит в следующий запуск.
6. **Альтернативный путь B. Deprecated модель.** FR-013: джоба прерывается, owner получает алерт, существующие векторы не трогаем.
7. **Альтернативный путь C. Сбой записи в pgvector.** Атомарность по NFR-UC1-004: объект остаётся в состоянии «грязный», в следующий запуск джобы попадает заново.
8. **Завершение.** Лог итогов (FR-014), снятие lock'а (FR-015), джоба завершается. Если через расписание триггер сработает раньше, чем закончилась предыдущая итерация — пропускается (FR-015).

**Идемпотентный re-run.** Если оператор / DevOps вручную запустят джобу сразу после её успешного завершения, FR-008 гарантирует: джоба не сделает ни одного платного вызова YC FM, отработает «вхолостую» за время одного запроса к SMP API.

## Бизнес-правила

- **BR-001. Whitelist атрибутов на векторизацию (baseline для PoC, требует sign-off Демьянова перед `issue`).** Источник: сводный whitelist в `content/10-domain/research/smp-metamodel.md`, секция «Сводный whitelist кандидатов». PII-метки: `low` / `medium` / `high`.

  | Класс | Атрибут | PII-риск | Включён в whitelist PoC |
  |---|---|:---:|:---:|
  | `knowledgeBase$article` | `title` | low | ✓ |
  | `knowledgeBase$article` | `description` | low | ✓ |
  | `knowledgeBase$article` | `content` | low | ✓ |
  | `knowledgeBase$article` | `keywords` | low | ✓ |
  | `knowledgeBase$section` | `title` | low | ✓ |
  | `knowledgeBase$section` | `description` | low | ✓ |
  | `knowledgeBase$section` | `keywords` | low | ✓ |
  | `problem` | `subject` | low | ✓ |
  | `problem` | `workaround` | low | ✓ |
  | `problem` | `rootCause` | low | ✓ |
  | `problem` | `description` | medium | ✓ (включается во второй гейт по problem) |
  | `problem` | `decisionReport` | medium | ✓ (включается во второй гейт по problem) |
  | `issue` | `subject` | medium | требует sign-off |
  | `issue` | `cancelReason` | low | требует sign-off |
  | `issue` | `description` | high | **НЕ включаем в PoC без явного решения owner'а + аудита** |
  | `issue` | `lastComment` | high | **НЕ включаем в PoC без аудита** |
  | `issue` | `feedback` | medium | требует sign-off |
  | `issue` | `decisionReport` | medium | требует sign-off |

- **BR-002. Один объект — одна актуальная векторная запись.** В pgvector хранится не более одной актуальной записи `(id_объекта, fqn, версия_модели)` на каждый объект SMP. Стратегия для нескольких векторов на объект (если выбираем хранение чанков по FR-006) — закрепится в ADR-YYY (chunk-aggregation).
- **BR-003. Версия модели эмбеддинга — обязательная часть записи.** В pgvector нельзя записать вектор без указания, какой моделью и какой версией модели он посчитан (для миграций по FR-009).
- **BR-004. Размерность вектора привязана к модели.** При смене модели на модель с другой размерностью — старые векторы становятся непригодны (несовместимая dim) и подлежат полному пересчёту через миграцию по ADR-YYY (model-versioning).
- **BR-005. Атрибуты вне whitelist'а — никогда не уходят во внешний сервис.** Это инвариант безопасности (CLAUDE.md, красные линии). Любая утечка whitelisted-атрибута, не описанного в BR-001, считается дефектом критической степени.
- **BR-006. Доступ к БД — только через SMP API.** Прямой JDBC-доступ из модуля к PostgreSQL запрещён архитектурно (CLAUDE.md). DDL-операции (создание/обновление индекса) — отдельный runbook DBA, не зона ответственности джобы.
- **BR-007. Failure не «токсичен» для данных.** Любой сбой векторизации одного объекта (ошибка YC FM, ошибка нормализации текста, ошибка записи) **не должен** изменять сами whitelisted-атрибуты SMP-объекта. Джоба пишет только в свои метаданные (`vector_dirty`, запись в pgvector).
- **BR-008. Тенант-изоляция.** Если на стенде несколько тенантов SMP, векторы тенанта A не попадают в выдачу для тенанта B. Реализация (отдельная таблица / discriminator-колонка) — закрепится в ADR-YYY (vector-storage-schema). Открытый вопрос: на стенде `llm2` — один тенант или несколько (см. секцию «Открытые вопросы»).

## Доменные события

- **VectorJobStarted** — джоба стартовала, в логе зафиксированы версия модели, целевые классы, размер батча.
- **VectorJobBatchCompleted** — батч обработан: число successful / skipped / failed.
- **VectorComputed** — для конкретного SMP-объекта вектор посчитан и сохранён, `vector_dirty` снят.
- **VectorComputeFailed** — для конкретного объекта векторизация провалена; объект остаётся «грязным».
- **VectorJobCompleted** — джоба завершилась нормально, итоговая статистика в логе.
- **VectorJobAborted** — джоба прервана (deprecated-модель, превышен time-cap, lock не снят) — owner получает алерт.
- **EmbeddingModelVersionChanged** — конфигурация модели эмбеддинга обновлена; в следующем запуске джоба должна провести full rescan по затронутым объектам.

## Acceptance Criteria

- [ ] **AC-001. Расписание.** На стенде `llm2` зарегистрирован `scheduledTask` модуля `pg_vector_service` с конфигурируемым расписанием; админ может изменить период без правок кода.
- [ ] **AC-002. Целевые классы — конфиг.** Список целевых FQN-классов задан в конфигурации модуля; добавление нового класса — без перекомпиляции JAR.
- [ ] **AC-003. Whitelist — конфиг.** Whitelist атрибутов на класс задан в конфигурации; smoke-проверка: при удалении любого атрибута из whitelist джоба перестаёт его отправлять в YC FM (проверяется через инспекцию исходящего payload в smoke-логе).
- [ ] **AC-004. Идемпотентность — повторный запуск.** Запуск джобы дважды подряд на одном и том же snapshot'е данных: на втором запуске количество исходящих вызовов YC FM = 0 (проверяется по логу/метрике).
- [ ] **AC-005. `vector_dirty` после изменения объекта.** При изменении whitelisted-атрибута существующего объекта `vector_dirty` устанавливается в true; в следующий запуск джобы этот объект попадает в выборку и пересчитывается. Способ выставления `vector_dirty` — на усмотрение SA (FR-007).
- [ ] **AC-006. Версия модели в записи.** Каждая запись в pgvector содержит непустое поле «версия модели эмбеддинга»; запись без этого поля считается невалидной и не создаётся (BR-003).
- [ ] **AC-007. Смена версии модели → пересчёт.** При обновлении конфигурации модели (имя или версия) запуск джобы пересчитывает векторы всех затронутых объектов; объекты, для которых пересчёт не успел завершиться, остаются помеченными как «грязные» и ждут следующего запуска (FR-009).
- [ ] **AC-008. PII-инвариант.** В smoke-тесте на стенде `llm2`: для тестового объекта класса `issue` с заполненным `description` (high-PII) и пустым `subject` исходящий payload в YC FM **не содержит** `description` (он не в whitelist'е PoC по BR-001). Проверка автоматическая, через инспекцию HTTP-вызова или mock-сервер.
- [ ] **AC-009. Rate limit / retry.** В smoke-тесте с искусственно ограниченной квотой YC FM (или через mock, отдающий 429): джоба делает retry с backoff'ом, при исчерпании ретраев — объект остаётся `vector_dirty` = true, попадает в следующий запуск, не теряется.
- [ ] **AC-010. Deprecated-модель → abort + alert.** В smoke-тесте с mock-ответом «модель deprecated»: джоба прерывается, owner получает алерт (канал — открытый вопрос), существующие векторы в pgvector остаются нетронутыми.
- [ ] **AC-011. Атомарность записи.** В smoke-тесте с искусственным сбоем после вызова YC FM, но до записи в pgvector: объект остаётся `vector_dirty` = true; в pgvector нет «полу-записи» (нет записи без версии модели или без вектора).
- [ ] **AC-012. Конкурентные запуски.** Ручной триггер джобы во время её работы — отклоняется (FR-015); в логе фиксируется причина «уже выполняется».
- [ ] **AC-013. JDBC отсутствует.** Code review модуля: ни одной прямой JDBC-зависимости в `src/`, все обращения к pgvector — через SMP API (BR-006). Проверяется автоматически (например, ban-list зависимостей в `pom.xml` / CodeNarc-правило).
- [ ] **AC-014. Логирование.** Лог одного запуска джобы содержит: VectorJobStarted, ≥1 VectorJobBatchCompleted, VectorJobCompleted (или VectorJobAborted при abort'е), для каждого failed-объекта — VectorComputeFailed с `correlationId`.

## Бриф для SA

**Требование:** `content/30-requirements/functional/uc1-scheduled-vectorization.md` (этот файл).
**Фаза:** PoC.

**Спроектировать:**
- Компоненты модуля: scheduler-entry, batch-processor, text-composer, embedding-client (YC FM adapter), pgvector-writer (через SMP API), dirty-tracker, model-version-manager.
- Интеграции: SMP API (read целевых объектов / write метаданных + pgvector), YC FM (REST + IAM-token), SMP scheduler (`api.scheduler`).
- Модель данных: схема pgvector-таблицы (id объекта, FQN, версия модели, вектор, timestamp), маркер `vector_dirty` (атрибут SMP / staging-таблица / mtime — выбрать в ADR), хранение конфигурации (whitelist, целевые классы, размер батча, версия модели).
- ADR-сессии (минимум):
    1. **ADR — Модель эмбеддинга и версионирование** (ссылается на FR-009, BR-003, BR-004).
    2. **ADR — Тип индекса pgvector + метрика расстояния** (опирается на `pgvector-indexes.md`).
    3. **ADR — Схема pgvector-таблицы и тенант-изоляция** (BR-008).
    4. **ADR — Стратегия dirty-tracking** (FR-007).
    5. **ADR — Нормализация richtext (HTML → plain) и чанкинг** (FR-005, FR-006).
    6. **ADR — Стратегия агрегации эмбеддингов чанков** (FR-006, BR-002).
    7. **ADR — Retry / backoff для YC FM** (FR-012).
    8. **ADR — Job locking и time-budget** (FR-015, FR-016).
    9. **ADR — Logging и alerting** (FR-013, FR-014).
    10. **ADR — Migration runbook при смене модели** (FR-009, BR-004).

**Бизнес-правила для валидаций:** BR-001 (whitelist), BR-003 (версия модели обязательна), BR-005 (за пределы whitelist'а ничего не уходит), BR-006 (только SMP API, без JDBC), BR-007 (сбой не портит данные).

**Acceptance criteria для проверки архитектуры:** AC-004 (идемпотентность), AC-006 (версия модели в записи), AC-008 (PII-инвариант — автоматически проверяемый), AC-011 (атомарность), AC-013 (отсутствие JDBC).

**Что НЕ решает SA в рамках UC1:**
- Sync-векторизация по событиям (out of scope требования).
- Семантику similarity-поиска (UC2).
- Алгоритмы кластеризации (UC3).

**Зависимости от research:** RES-002 (verify YC FM model + dim + limits + pricing — на момент написания заблокирован CAPTCHA, см. `yc-foundation-models.md`), RES-003 (budget-estimate), OQ-IDX-1/2/3/7 из `pgvector-indexes.md` (версия pgvector на стенде, стратегия DDL, `maintenance_work_mem`, схема/tablespace).
