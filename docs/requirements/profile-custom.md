# Профиль custom — функтребования

## Контекст

Профиль `custom` — catch-all для случаев, когда ни один из 6 других профилей не подходит: research-каталог, личный wiki, методология с нестандартной структурой, эксперимент, смешанный контент.

Ключевой принцип: **anti-opinion**. Профиль не навязывает структуру, нумерацию, workflow или ролевую модель. Пользователь получает минимальный baseline — Gramax-видимый каталог с примерами — и строит всё остальное самостоятельно.

**Non-goal:** стандартизировать подход к документации для пользователей custom. Если нужна стандартизация — выбери другой профиль.

**Целевые пользователи:**
- Исследователь, ведущий личный wiki в Gramax
- Команда с уникальной методологией, не покрытой профилем `methodology`
- Пользователь, который хочет начать с чистого листа и посмотреть, что получится

## Структурные требования

### content-scaffold/

Минимальный scaffold — ровно столько, чтобы Gramax увидел каталог и пользователь имел рабочие примеры:

```
content-scaffold/
├── _index.md                        # корень каталога (Gramax-обязательный)
├── templates/
│   ├── _index.md
│   ├── article-example.md           # пример обычной заметки/статьи
│   ├── decision-example.md          # пример решения (ADR-лайт: контекст → решение → последствия)
│   └── reference-example.md         # пример справочной статьи (термин/сущность + описание)
└── inbox/
    └── _index.md                    # место для необработанных материалов
```

Папка `inbox/` включается в scaffold как нейтральный staging area — её семантика не навязывает обработку (пользователь может переименовать или удалить). Числовые префиксы (`10-`, `20-`) не используются нигде в scaffold.

### subagents

| Роль | Статус | Обоснование |
|------|--------|-------------|
| pm | core | Координация минимального контекста нужна всегда |
| researcher | optional | Единственная роль, уместная без предметного контекста: сбор информации полезен в любом каталоге |
| ba | optional | Если пользователь захочет формализовать требования — доступен |
| tech-writer | optional | Если появится потребность в структурированном тексте — доступен |
| sa | optional | Доступен при необходимости; custom не предполагает архитектурных задач по умолчанию |
| dev | optional | Доступен, если custom вырос в delivery-проект |
| devops | optional | Доступен по необходимости |
| qa | optional | Доступен по необходимости |
| devsecops | optional | Доступен по необходимости |
| compliance | optional | Доступен по необходимости |

Логика: pm = core (техническая необходимость координации), researcher = optional как единственная содержательно-уместная роль без контекста, все остальные = optional (пользователь активирует по потребности). Никаких disabled — custom не знает, что понадобится.

### agent_overrides

**Решение: НЕТ overrides.**

Custom — anti-opinion профиль. Любой agent override навязывает стиль или workflow, что противоречит принципу. Если пользователю нужен специализированный агент — он выбирает другой профиль или настраивает агента вручную после init. Добавление overrides потребовало бы конкретного обоснования, а у custom нет предметного контекста для такого обоснования.

### .doc-root.yaml properties

Минимальный набор — только два поля:

| Property | Required | Values |
|----------|----------|--------|
| Тип контента | yes | Заметка, Решение, Справка (или свободная строка — SA решает) |
| Статус | yes | Draft / Review / Approved / Archived |

Поля из других профилей явно исключены: Версия продукта (kb-product), Аудитория (kb-product), Уровень сложности (course), Область применения (methodology), Фаза (project). Если пользователю нужны domain-специфичные поля — он добавляет их вручную в `.doc-root.yaml` после init.

## Operations

При init custom выполняются следующие операции:

- `op:add content-scaffold/` — добавить минимальный scaffold (`_index.md`, `templates/`, `inbox/`)
- `op:replace doc-root.yaml` — заменить `.doc-root.yaml` на минимальный вариант (Тип контента + Статус)
- `op:delete 10-domain/` — удалить, если присутствует в baseline
- `op:delete 20-project/` — удалить, если присутствует в baseline
- `op:delete 30-requirements/` — удалить, если присутствует в baseline
- `op:delete 40-architecture/` — удалить, если присутствует в baseline
- `op:delete 50-delivery/` — удалить, если присутствует в baseline
- `op:delete 60-implementation/` — удалить, если присутствует в baseline
- `op:delete 70-operations/` — удалить, если присутствует в baseline

Итог: только `_index.md` + `templates/` + `inbox/` от delivery-baseline не остаётся ничего.

## Out of scope (явно зафиксировано)

- Никаких standardized workflows — порядок работы пользователь определяет сам
- Никаких force-conventions нумерации папок — числовые префиксы anti-pattern для custom
- Никаких core agent overrides — профиль не знает, что нужно пользователю
- Никаких compliance / domain-specific properties в `.doc-root.yaml`
- Никаких pipeline-ов — custom не активирует `/pipelines/project-planning` или другие

## Anti-pattern AC

AC, проверяемые после `init --profile custom`:

- **APC-001:** В `content/` отсутствуют папки с числовыми префиксами (`10-*`, `20-*`, `30-*` и т.д.) — ни в scaffold, ни добавленные операциями.
- **APC-002:** В `content/` отсутствует папка `requirements/` или `30-requirements/` — custom не подразумевает BA-workflow.
- **APC-003:** В `content/` отсутствует папка `adr/` или `40-architecture/` — custom не подразумевает SA-workflow.
- **APC-004:** В `docs/overlays/profiles/custom/agent-overrides/` отсутствуют файлы — ни одного agent override не создано.
- **APC-005:** `.doc-root.yaml` не содержит полей `Версия продукта`, `Аудитория`, `Уровень сложности`, `Область применения`, `Фаза` — только `Тип контента` и `Статус`.

## Бриф для SA

**Требование:** `docs/requirements/profile-custom.md` — **Фаза:** W4c-A

**Спроектировать:**
- Содержимое `content-scaffold/` для custom (3 файла templates + inbox + корневой _index)
- Минимальный `doc-root.yaml` (Тип контента enum vs free string — решение на усмотрение SA с обоснованием)
- Подтвердить или уточнить список `op:delete` операций для очистки delivery-baseline

**Бизнес-правила для валидаций:**
- Числовые префиксы в папках scaffold = ошибка
- Наличие agent-overrides файлов = ошибка
- `.doc-root.yaml` с более чем 2 полями = предупреждение (нужно обоснование)

**Acceptance criteria для проверки архитектуры:**
- APC-001..005 проходят после `init --profile custom`
- Scaffold содержит ровно 3 template-файла + inbox + корневой _index
- `manifest.yaml` обновлён до `status: stable` и содержит корректные operations
