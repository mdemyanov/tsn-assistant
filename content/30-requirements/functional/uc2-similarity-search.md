# UC2 — Семантический поиск похожих SMP-объектов

Use case 2 проекта `pg_vector_service`: top-K similarity search по векторным
представлениям SMP-объектов (`issue`, `knowledgeBase$article`, `problem`).
Опирается на векторы, наполняемые джобой UC1 (out of scope здесь), и на
методологию оценки качества из `content/10-domain/research/similarity-eval.md`.

## Описание

UC2 предоставляет потребителям SMP единый интерфейс «найди похожих»: по
заданному объекту (`issue` / `kb-article` / `problem`) или по произвольному
тексту-запросу модуль возвращает top-K объектов, ранжированных по
семантической близости их векторных представлений.

Поиск выполняется поверх векторного индекса pgvector, наполняемого UC1.
Запрос принимается через SMP-слой (точные API-контракты — задача SA);
ответ — упорядоченный список ссылок на SMP-объекты с оценкой сходства и
служебными метаданными (класс, статус, идентификатор). Получатель ответа
(карточка заявки, форма редактирования KB, отчётная джоба) сам решает,
как отображать или агрегировать результат — UC2 отдаёт **данные**, не UI.

UC2 поддерживает три режима поиска:

- **same-class** — `issue → issue`, `kb → kb`, `problem → problem`;
- **cross-class** — `issue → kb-article`, `issue → problem`, `kb-article →
  problem` (возможны и обратные направления);
- **free-text** — поисковая строка (например, текст черновика заявки до
  её сохранения) → top-K объектов любого из векторизованных классов.

Решение по тому, как технически реализована cross-class similarity (один
общий векторный индекс на все целевые классы, отдельные индексы с union
на стороне сервиса или иной механизм), — закрепится в **ADR-YYY**.

UC2 — read-only по отношению к SMP. Никаких записей в карточки SMP не
производится; отметки «связанная заявка», «дубль», «связанная проблема»
ставит оператор / аналитик вручную или это делает отдельный сценарий
(UC3 — кластеризация дублей, out of scope).

## Функциональные требования

- **FR-001.** Сервис принимает запрос «найти похожих» по идентификатору
  существующего SMP-объекта (FQN + UUID) и возвращает упорядоченный
  список top-K объектов с оценкой сходства.
- **FR-002.** Сервис принимает запрос «найти похожих» по произвольной
  текстовой строке (free-text) и возвращает аналогичный список.
- **FR-003.** Параметр K — настраиваемый на уровне запроса. Значение по
  умолчанию — **10**. Допустимый диапазон значений и верхний предел
  фиксируются в **ADR-YYY** (предложение BA: верхняя граница ≤ 100,
  чтобы не утяжелять отклик и не побуждать обходить UC3).
- **FR-004.** Запрос принимает фильтр по целевому классу (whitelist FQN):
  `issue`, `knowledgeBase$article`, `problem` и их подклассы. Если фильтр
  не задан — поиск идёт по всем классам, для которых построены векторы.
- **FR-005.** Запрос поддерживает same-class и cross-class режимы (см.
  «Описание»). Способ реализации — на усмотрение SA (**ADR-YYY**).
- **FR-006.** Результат поиска содержит для каждой записи минимум:
  FQN целевого объекта, его идентификатор, оценку сходства (числовое
  значение, диапазон фиксируется в SA), статус workflow на момент запроса.
  Расширенный набор атрибутов в ответе — на усмотрение SA.
- **FR-007.** Сервис исключает из выдачи **сам объект-источник** запроса
  (если поиск идёт от существующего объекта) — он не должен возвращаться
  в top-K как «похожий сам на себя».
- **FR-008.** Сервис применяет фильтр прав доступа к KB-статьям: при
  поиске под учётной записью пользователя U не возвращает статьи KB, к
  которым у U нет доступа согласно `kbAccesses` (см. BR-002).
- **FR-009.** Сервис применяет фильтр статусов workflow: по умолчанию
  исключает из выдачи объекты в финальных «нерабочих» статусах (для KB —
  `closed`; для issue/problem — статусы, помеченные как «отменено» / «не
  актуально»). Точный перечень статусов фиксируется в **ADR-YYY**, режим
  «искать в том числе по закрытым» — опциональный параметр запроса.
- **FR-010.** Сервис возвращает ошибку с осмысленным кодом, если: объект-
  источник не найден; класс источника не входит в whitelist
  векторизуемых; вектор для источника ещё не построен (race с джобой UC1).
  Структура ответа об ошибке — задача SA (без stack-traces наружу).
- **FR-011.** Сервис логирует каждый запрос с `correlationId`, набором
  параметров (без полного текста free-text — PII-риск, см. BR-004),
  длительностью и количеством результатов. Формат лога — задача DevOps.

## Нефункциональные требования

- **NFR-001 (latency, черновой).** End-to-end время ответа `p95 ≤ 200 ms`
  на корпусе порядка 100k объектов при HNSW-индексе с параметрами по
  умолчанию (см. `content/10-domain/research/pgvector-indexes.md §3.1`,
  `ef_search=40`). Финальный SLA фиксирует SA в **ADR-YYY** после первого
  smoke-замера на стенде `llm2`.
- **NFR-002 (качество, черновой).** На offline-evaluation (методология
  `similarity-eval.md §5`):
    - `Recall@10 ≥ 0.80` (primary);
    - `MRR@10 ≥ 0.50` (primary).
  Финальные пороги для go/no-go PoC подтверждаются после offline-eval —
  фиксируются в **ADR-YYY**.
- **NFR-003 (изоляция тенанта).** Поиск должен возвращать объекты только
  того тенанта SMP, в контексте которого выполнен запрос. Векторы разных
  тенантов смешиваться в выдаче не должны. (Мульти-тенантность для PoC —
  один тенант `llm2`, но требование инвариантно фазе.)
- **NFR-004 (безопасность данных).** Никаких сырых текстов SMP-объектов в
  ответе UC2 не возвращается, кроме явно whitelisted полей (см. BR-004).
  Ответ содержит ссылки на объекты — клиент при необходимости получает
  тексты через штатные SMP-API.
- **NFR-005 (предсказуемость).** При отсутствии совпадений сервис возвращает
  пустой список (а не ошибку) — потребитель должен корректно обрабатывать
  кейс «похожих не найдено».

## User Journey

### Journey-1. Оператор Service Desk на карточке заявки

1. Оператор открывает карточку заявки `I` (`issue$incident`).
2. UI карточки запрашивает у UC2 top-10 похожих объектов: класс
   источника — `issue`, целевые классы — `issue`, `knowledgeBase$article`,
   `problem`.
3. UC2 проверяет наличие вектора для `I`. Если вектора нет — возвращает
   пустой список + статус «vector not ready» (FR-010); UI отображает
   плашку «Похожие пока считаются».
4. UC2 выполняет поиск, применяет фильтры `kbAccesses` и статусов
   (FR-008, FR-009), исключает сам `I` из выдачи (FR-007).
5. UI отображает три коротких списка: «Похожие заявки», «Связанные
   статьи KB», «Возможные проблемы».
6. Оператор кликает по любой из ссылок — переходит на карточку
   соответствующего объекта средствами SMP.

**Альтернативный путь.** Если у оператора нет доступа к KB-статье,
которая семантически наиболее близка, она в выдаче не появится (BR-002),
а на её месте окажется следующая по релевантности доступная статья.

### Journey-2. Автор статьи KB перед публикацией

1. Автор готовит черновик новой KB-статьи; в форме есть кнопка
   «Найти похожие».
2. UI отправляет в UC2 free-text запрос (FR-002): `title + content`
   черновика, фильтр по классу `knowledgeBase$article`.
3. UC2 строит embedding free-text запроса, выполняет поиск в индексе KB.
4. UI отображает список из top-10 ближайших опубликованных статей со
   ссылками и оценкой сходства.
5. Автор оценивает результаты и принимает решение: публиковать новую,
   расширить существующую или вложить как раздел.

**Альтернативный путь.** Если черновик содержит < N символов, UI может
не запускать запрос (порог UI; в требование не входит — выбор клиента).

### Journey-3. Аналитик качества — агрегированный отчёт

1. Аналитик выбирает «эталонную» заявку `I_ref`, типичную для разбираемого
   класса инцидентов.
2. Аналитик запускает джобу / отчёт, который вызывает UC2 с параметрами:
   источник = `I_ref`, класс = `issue`, K = 100 (или другое значение в
   допустимом диапазоне FR-003), фильтр статусов выключен (включая
   закрытые).
3. UC2 возвращает список «похожих» заявок.
4. Отчётная джоба группирует список по подклассам (`issue$incident` /
   `issue$SAP` / …), услуге (`slmService`), исполнителю и формирует
   сводку.
5. Аналитик передаёт сводку в обсуждение «инициировать ли проблему /
   изменение услуги».

**Альтернативный путь.** Если в выдаче UC2 есть заявки уже связанные с
существующей `problem` (через `problem.issues`), джоба отдельно
сигнализирует «возможно, всё это про проблему `P_x`».

## Бизнес-правила

- **BR-001. Источник объект-источника обязателен и валиден.** Запрос «по
  объекту» допустим только для FQN из whitelist векторизуемых классов
  (UC1). Если класс источника не векторизован — UC2 возвращает ошибку
  (FR-010), а не «поиск по произвольному тексту по умолчанию» (чтобы не
  скрывать ошибку UC1).
- **BR-002. Учёт `kbAccesses`.** Любая KB-статья (`knowledgeBase$article`)
  возвращается в выдаче UC2, **только** если у пользователя, в контексте
  которого выполняется запрос, есть доступ согласно `kbAccesses` (см.
  `smp-metamodel.md §knowledgeBase`). Способ проверки (на стороне SMP-API
  фильтрацией по доступам или предварительным фильтром в pgvector-запросе)
  — задача SA, **ADR-YYY**.
- **BR-003. Исключение объекта-источника.** Объект-источник никогда не
  присутствует в выдаче top-K (FR-007), независимо от схожести.
- **BR-004. Защита PII в логах и ответах.** В логах UC2 не сохраняется
  полный текст free-text запроса и не сохраняется decryptable hash от
  него; допустим только усечённый отпечаток (например, длина и хэш) —
  конкретный формат фиксирует SA в **ADR-YYY** с учётом требований UC1
  на whitelist атрибутов.
- **BR-005. Ground truth для оценки качества.** Качество UC2 (NFR-002)
  оценивается по методологии `similarity-eval.md §4` — ground truth
  собирается без ручной разметки из `issue.duplicates` /
  `duplicatesRL`, `problem.issues`, `slmService`. Бинарная или
  градированная разметка — открытый вопрос (Q3 ниже), решение в **ADR-YYY**.
- **BR-006. Изоляция тенанта.** UC2 никогда не возвращает объекты тенанта,
  отличного от тенанта запроса (NFR-003). Способ изоляции — задача SA.
- **BR-007. Отсутствие записи в SMP.** UC2 не модифицирует SMP-объекты.
  Любые «связать как дубль», «прикрепить к проблеме» и т. п. — действия
  потребителя, а не UC2 (UC3 — out of scope).
- **BR-008. Согласованность с UC1 по атрибутам.** Качество UC2 напрямую
  зависит от того, какие атрибуты UC1 включил в композитный текст
  эмбеддинга и какой моделью векторизовал. При смене модели или whitelist
  атрибутов в UC1 — UC2 переоценивается (новый прогон evaluation), даже
  если код UC2 не изменился.

## Доменные события

- **SimilaritySearchRequested** (`source`, `targetClasses`, `K`, `mode`,
  `correlationId`) → UC2 принял запрос, начал обработку.
- **SimilaritySearchCompleted** (`correlationId`, `resultCount`,
  `latencyMs`) → запрос обработан, результат отправлен потребителю.
- **SimilaritySearchFailed** (`correlationId`, `errorCode`, `reason`) →
  ошибка обработки (вектор не готов / класс не векторизуется / др.).
- **VectorMissing** (`source`, `correlationId`) → специализация Failed:
  UC2 не нашёл вектор источника. Триггер для джобы UC1 / алерта DevOps.

Перечень — кандидатный, окончательный набор и формат событий
закрепляется в **ADR-YYY** (контракт SPI / интеграция в наблюдаемость
проекта).

## Acceptance Criteria

- [ ] AC-1. Запрос «найти похожих» по существующему объекту
  (`issue` / `knowledgeBase$article` / `problem`) возвращает top-K
  результатов с K = 10 по умолчанию (FR-001, FR-003).
- [ ] AC-2. Запрос с явным K возвращает ровно K записей или меньше
  (если в индексе меньше доступных кандидатов) и не возвращает больше
  (FR-003).
- [ ] AC-3. Free-text запрос возвращает результаты, отличные от пустого
  множества, на репрезентативной выборке тестовых строк (FR-002).
- [ ] AC-4. Запрос с фильтром `targetClasses = [knowledgeBase$article]`
  не возвращает в выдаче ни одного `issue` или `problem` (FR-004).
- [ ] AC-5. Cross-class запрос (`source = issue`, `targetClasses =
  [knowledgeBase$article, problem]`) возвращает объекты обоих типов в
  одной упорядоченной по сходству выдаче (FR-005).
- [ ] AC-6. Объект-источник никогда не присутствует в результатах
  (FR-007, BR-003) — проверяется на 100 случайных запросов.
- [ ] AC-7. Под пользователем без доступа к KB-разделу `S` ни одна
  статья из `S` не возвращается, даже если её косинус-близость к
  источнику максимальна. Под пользователем с полным доступом — те же
  статьи возвращаются (BR-002, FR-008).
- [ ] AC-8. Объекты в финальных «нерабочих» статусах (`closed` для KB,
  отменённые для issue/problem) не возвращаются по умолчанию (FR-009).
  Запрос с включённым параметром «искать в том числе по закрытым» —
  возвращает.
- [ ] AC-9. Запрос об объекте, для которого ещё не построен вектор,
  возвращает корректную ошибку «vector not ready» (FR-010), а не пустой
  список и не 500.
- [ ] AC-10. Запрос об объекте тенанта `T1` под учёткой тенанта `T2` не
  возвращает результатов из `T1` (NFR-003, BR-006). На PoC проверяется
  концептуально на одном тенанте (через имитирующие фикстуры) — полная
  проверка на Pilot.
- [ ] AC-11. **(Качество, черновой).** На offline-evaluation согласно
  методологии `similarity-eval.md §5`: `Recall@10 ≥ 0.80`, `MRR@10 ≥
  0.50` (NFR-002). **Итоговые пороги — после offline-eval, в ADR-YYY.**
- [ ] AC-12. **(Latency, черновой).** На корпусе ≥ 100k объектов после
  warm-up (`similarity-eval.md §3.2`): `p95 ≤ 200 ms` end-to-end
  (NFR-001). **Итоговые пороги — после первого smoke-замера, в
  ADR-YYY.**
- [ ] AC-13. Логи UC2 содержат `correlationId`, длительность и кол-во
  результатов; не содержат полный текст free-text запроса (BR-004,
  FR-011).
- [ ] AC-14. Любая ошибка возвращается без stack-trace в теле ответа
  (CLAUDE.md «Красные линии»); stack — в логах с `correlationId`.
