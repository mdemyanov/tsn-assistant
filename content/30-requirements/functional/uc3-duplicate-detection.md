## JTBD

**Оператор Service Desk:**
Когда я регистрирую новую заявку, я (оператор Service Desk) хочу видеть до 3-5 уже существующих заявок, похожих по содержанию на регистрируемую,
чтобы быстро понять «это дубль уже принятой заявки» или «это вариация известной проблемы», избежать повторной диагностики и предложить заявителю готовое решение или ссылку на родительский тикет.

**Аналитик качества:**
Когда я провожу еженедельный аудит очереди и базы проблем, я (аналитик качества) хочу получать отчёт «N кандидатов на слияние» с группами потенциально однотипных объектов,
чтобы целенаправленно прорабатывать накопившиеся дубли, выявлять системные проблемы (одна root cause → много заявок) и поддерживать чистоту базы знаний и реестра проблем.

## Описание

Use Case 3 закрывает два смежных сценария на основе уже посчитанных эмбеддингов SMP-объектов (см. UC1 — векторизация джобой по расписанию):

- **Сценарий А — online-подсказка на новой заявке.** В момент регистрации заявки оператором система ищет среди уже векторизованных `issue` ближайших соседей по cosine similarity и предлагает оператору список кандидатов в дубли с пометкой уровня уверенности («дубль» / «похожая»). Никаких автоматических действий — только подсказка в UI; решение о связывании или мёрже принимает человек.
- **Сценарий Б — batch-аудит (раз в неделю).** Регулярная джоба проходит по корпусу `issue` и `problem` за заданное окно (например, последние 3 месяца) и формирует отчёт с группами потенциально дублирующихся объектов: пары и (если хватит данных и алгоритма) многоэлементные группы. Отчёт получает аналитик качества; список разбора объектов ведётся вручную.

Для PoC главная цель — проверить, что качество near-duplicate detection поверх эмбеддингов Yandex FM достаточно для практического использования в Service Desk и что precision рекомендаций не превращает их в «шум, который оператор отключит после первого дня». В качестве ground truth используются проставленные операторами связи `issue.duplicates` / `issue.duplicatesRL`.

KB-кластеризация (тематическая группировка статей), кросс-классовая кластеризация (`issue` ↔ KB), а также построение кластеров «на лету» при каждом обновлении объекта — out of scope PoC.

## Функциональные требования

### Сценарий А — online-подсказки на новой заявке

- **FR-001.** При регистрации новой заявки `issue` (создание объекта или открытие формы регистрации с заполненными `subject` + `description`) система должна возвращать список из не более чем `N=5` ближайших по семантическому сходству ранее зарегистрированных заявок.
- **FR-002.** Поиск похожих ведётся среди уже векторизованных объектов того же класса (по подклассу `issue` определяется тенант / тип — конкретику закрепит SA).
- **FR-003.** Каждому кандидату в результате поиска присваивается **уровень совпадения** на основе cosine similarity:
  - **Дубль** — совпадение выше высокого порога (черновое значение `≥ 0.92`).
  - **Похожая** — совпадение в среднем диапазоне (черновое значение `0.85 … 0.92`).
  - Кандидаты ниже нижнего порога (`< 0.85`) **не возвращаются**.
- **FR-004.** Кандидат-кандидат с тем же `id`, что и регистрируемая заявка, должен исключаться из выдачи (защита от self-match при повторном вычислении эмбеддинга).
- **FR-005.** Кандидаты, к которым у текущего оператора нет прав доступа в SMP, должны исключаться из выдачи (наследовать стандартные ACL SMP, не обходить).
- **FR-006.** Для каждого кандидата система возвращает минимум: SMP-идентификатор (FQN + `id` или `UUID`), `subject`, статус, similarity score, метку уровня (`Дубль` / `Похожая`).
- **FR-007.** Действия оператора над кандидатом (связать как дубль, проигнорировать, открыть в новой вкладке) — out of scope этого требования; UI-обвязка определяется в SA-фазе и зависит от точки внедрения (форма регистрации SMP / отдельная панель).
- **FR-008.** Если за разумное время поиск не успел отработать (см. NFR), система должна тихо отказаться от подсказки — оператор не должен видеть ошибку или «висящий» спиннер на форме регистрации.

### Сценарий Б — batch-аудит дублей

- **FR-009.** Раз в заданный период (черновое значение — еженедельно, **итоговую частоту фиксирует SA в ADR**) запускается джоба, которая по корпусу `issue` и `problem` формирует группы потенциально однотипных объектов.
- **FR-010.** Окно объектов для batch-аудита параметризуемо (например, «последние 90 дней по дате регистрации», «открытые + закрытые за период»). Конкретные дефолты — open question.
- **FR-011.** На выходе джоба формирует **отчёт «кандидаты на слияние»** со списком групп; для каждой группы — список SMP-объектов, средняя/минимальная similarity внутри группы, тип (issue / problem), краткие признаки (тема первого объекта в группе).
- **FR-012.** Группы, целиком состоящие из объектов, уже связанных через `issue.duplicates` / `issue.duplicatesRL`, помечаются в отчёте как «известные» и не требуют действий аналитика — но из отчёта не удаляются (полезно для оценки полноты автоматической детекции).
- **FR-013.** Аналитик качества получает отчёт в виде, согласованном на этапе SA (черновой кандидат: статья в KB или файл в `content/70-operations/`; формат — open question).
- **FR-014.** Применимость: `issue` (главный use case), `problem` (вторичный). KB и кросс-классовые группы — out of scope PoC.

### Качество и оценка

- **FR-015.** Для оценки качества обоих сценариев используется ground truth из SMP — связи `issue.duplicates` и `issue.duplicatesRL`, ранее проставленные операторами вручную.
- **FR-016.** Реализуется offline-evaluation скрипт / процедура: на размеченном срезе вычисляются метрики **Precision @ T** и **Recall @ T** для сетки порогов `T ∈ {0.80, 0.85, 0.90, 0.92, 0.95}` (точная сетка — на усмотрение SA / Researcher).
- **FR-017.** Финальные значения порогов `Дубль` / `Похожая` для PoC закрепляются в ADR на основе offline-eval; до публикации ADR используются черновые значения из FR-003.

## Нефункциональные требования

- **NFR-001 (online latency).** Подсказка похожих заявок (FR-001) появляется в UI оператора не позже **2 секунд** с момента запроса. Если ответ не успевает — см. FR-008 (silent skip). Итоговый бюджет — на ревизии после первого smoke на стенде `llm2`.
- **NFR-002 (online throughput).** Сценарий А должен переживать пиковую нагрузку очереди регистрации Service Desk без деградации векторного поиска. Целевое значение пика — open question (зависит от профиля стенда — фиксируется по итогам RES-001 / DevOps-замера).
- **NFR-003 (batch window).** Джоба сценария Б укладывается в окно ночного обслуживания SMP (черновой бюджет — **до 4 часов** при объёме «несколько сотен тысяч векторов»). Превышение — триггер пересмотра алгоритма (см. брифу для SA про резервный путь HDBSCAN+UMAP).
- **NFR-004 (precision).** На сценарии А precision рекомендаций уровня `Дубль` (по сравнению с `issue.duplicates` как ground truth) — **не ниже 0.80** (false positive rate ≤ 20%). Цель: оператор не должен утонуть в ложных предложениях.
- **NFR-005 (recall).** На сценарии А recall дубликатов — **не ниже 0.50**. Допускается пропуск части дубликатов; принципиально, чтобы то, что система предложила, было релевантным.
- **NFR-006 (PII).** В тексте отчёта batch-аудита и в ответе online-сценария — **только идентификаторы и темы** (`subject`); полное `description` не возвращается клиенту в составе подсказки. Развёрнутый просмотр — через стандартный SMP-UI по ссылке, под существующими ACL.
- **NFR-007 (idempotence).** Повторный запуск batch-джобы на тех же входных данных и с теми же параметрами должен давать сопоставимые группы (в пределах недетерминизма используемого алгоритма; конкретные требования к стабильности — итоговая формулировка в SA).
- **NFR-008 (наблюдаемость).** Каждый запуск batch-джобы пишет в лог (или в структурированный отчёт): размер входной выборки, число найденных групп, число пар-дублей, длительность, идентификатор модели эмбеддингов, использованные пороги.

## User Journey

### Сценарий А — online на регистрации заявки (happy path)

1. Заявитель звонит оператору, оператор открывает форму регистрации `issue`.
2. Оператор заполняет `subject` («Не открывается VPN на ноутбуке») и `description`.
3. Система вычисляет (или достаёт из кеша — реализация на SA) эмбеддинг по композитному тексту regiстрируемой заявки.
4. Система запрашивает top-K ближайших соседей среди уже векторизованных `issue`.
5. Кандидаты с similarity ниже нижнего порога отфильтровываются. Кандидаты, к которым у оператора нет ACL, отфильтровываются.
6. Оставшиеся кандидаты (≤ 5 шт.) показываются оператору с метками `Дубль` / `Похожая` и `subject`.
7. Оператор:
   - либо вручную связывает новую заявку с одним из кандидатов как дубль (через стандартный механизм `issue.duplicates`);
   - либо игнорирует подсказку и продолжает регистрацию.
8. Никаких автоматических действий с заявками или кандидатами не выполняется.

**Альтернативный путь A1 (нет похожих).** Шаги 1-5; на шаге 6 список пуст — UI показывает «Похожих заявок не найдено» либо вовсе не показывает блок (UX-решение SA).

**Альтернативный путь A2 (timeout).** Шаги 1-3; шаг 4 не уложился в NFR-001 — система silent skip, оператор продолжает регистрацию, как если бы UC3 не существовал. В лог пишется событие таймаута.

**Альтернативный путь A3 (нет векторизации).** Если ни одна заявка ещё не векторизована (cold start) — выдача пуста, ошибки нет.

### Сценарий Б — batch-аудит (happy path)

1. По расписанию запускается джоба `duplicate-audit`.
2. Джоба выгружает срез векторов (`issue` и `problem`) за окно (FR-010).
3. Алгоритм обнаружения групп (выбор алгоритма — задача SA, см. бриф) выдаёт группы потенциально однотипных объектов.
4. Группы, полностью покрытые существующими `issue.duplicates`, помечаются как «известные».
5. Формируется отчёт «N кандидатов на слияние» с метаданными группы.
6. Отчёт публикуется в канале / месте, согласованном с аналитиком (KB / шара / письмо — open question).
7. Аналитик качества разбирает отчёт вручную: какие группы реально слить, какие — оставить, какие — превратить в `problem`.
8. Никаких автоматических связываний / мёрджей джоба не делает.

**Альтернативный путь Б1 (превышение окна).** Если джоба не укладывается в NFR-003 — она аварийно прекращается, пишет событие в лог, **никакого частичного отчёта** не публикует (чтобы аналитик не работал по обрывкам). Эскалация — DevOps + пересмотр стратегии в SA.

## Бизнес-правила

- **BR-001.** **Никакого автомёрджа в PoC.** Любое связывание заявок как дублей или слияние объектов выполняется вручную оператором (сценарий А) или аналитиком качества (сценарий Б). Система — только источник подсказок и отчётов.
- **BR-002.** Ground truth для оценки качества — связи `issue.duplicates` и `issue.duplicatesRL`, проставленные операторами SMP вручную. Иные источники разметки в PoC не используются.
- **BR-003.** Подсказки и отчёты UC3 не могут содержать SMP-объекты, к которым у получателя (оператора / аналитика) нет прав доступа в SMP. Стандартные ACL SMP не обходятся.
- **BR-004.** Полный текст `description`, `lastComment` и других потенциально PII-содержащих атрибутов в подсказках UC3 не отображается. Видимы только `subject` и метаданные. Подробности — переход в стандартный SMP-UI.
- **BR-005.** Если новая заявка ещё не имеет эмбеддинга на момент регистрации (например, джоба векторизации UC1 ещё не отработала на ней) — это допустимое состояние; UC3 либо вычисляет ad-hoc эмбеддинг, либо тихо пропускает подсказку (выбор фиксируется в SA).
- **BR-006.** Все запросы к Yandex Cloud FM, делающие ad-hoc embedding (если такой режим выбран в SA), идут только по уже разрешённому в UC1 whitelist'у атрибутов — никаких новых полей.
- **BR-007.** Решения, по которым ground truth `issue.duplicates` отсутствует целиком (например, для `problem`), оцениваются качественно — экспертная проверка аналитиком на нескольких группах из отчёта PoC; формальные precision/recall для таких классов не публикуются как PoC-метрика.

## Доменные события

- **`SimilarIssuesRequested`** (online) — оператор открыл подсказку похожих на форме регистрации. Атрибуты: id оператора, черновой `subject`, число возвращённых кандидатов, длительность.
- **`SimilarIssuesSkipped`** (online) — silent skip по таймауту или отсутствию эмбеддинга. Атрибуты: причина (timeout / no-embedding / no-candidates).
- **`DuplicateAuditRunStarted`** (batch) — джоба сценария Б стартовала. Атрибуты: окно, размер выборки, идентификатор модели эмбеддингов, использованные пороги.
- **`DuplicateAuditRunCompleted`** (batch) — джоба завершилась. Атрибуты: число групп, число пар-дублей, число «известных» групп, длительность.
- **`DuplicateAuditRunFailed`** (batch) — джоба не уложилась в окно или упала. Атрибуты: причина, момент остановки.

## Acceptance Criteria

- [ ] **AC-001.** На размеченном срезе `issue` (объекты с проставленным `duplicates` / `duplicatesRL`) precision рекомендаций уровня `Дубль` ≥ **0.80** при черновых порогах из FR-003 (итоговые пороги — после offline-eval, ADR).
- [ ] **AC-002.** На том же срезе recall рекомендаций уровня `Дубль` ≥ **0.50**.
- [ ] **AC-003.** Online-подсказка на форме регистрации возвращает результат не позже **2 секунд** на 95-м перцентиле (стенд `llm2`, нагрузка профиля smoke). Итоговое значение latency — после первого замера, фиксируется в DevOps-отчёте.
- [ ] **AC-004.** Подсказка online не показывает заявок, к которым у оператора нет ACL (выборочная проверка на тестовом аккаунте без прав).
- [ ] **AC-005.** Подсказка online не содержит полного `description` или `lastComment` — только `subject` + метаданные (визуальный smoke).
- [ ] **AC-006.** Batch-джоба отрабатывает на полном срезе `issue` + `problem` за окно (FR-010) в пределах NFR-003. Отчёт сформирован, содержит хотя бы одну группу.
- [ ] **AC-007.** В отчёте batch-аудита группы, полностью покрытые существующими `issue.duplicates`, помечены как «известные» и видимо отделены от новых кандидатов.
- [ ] **AC-008.** Повторный запуск batch-джобы на тех же входных данных и с теми же параметрами даёт сопоставимый набор групп (детерминированность в пределах алгоритма — точные требования закрепит SA).
- [ ] **AC-009.** Никаких автоматических связываний / мёрджей по `issue.duplicates` в журнале SMP за время работы PoC — system-of-record не модифицируется без участия оператора / аналитика.
- [ ] **AC-010.** Журнал событий (NFR-008) содержит идентификатор модели эмбеддингов и пороги для каждого запуска batch-джобы — позволяет воспроизвести результат после смены модели.

| Q10 | Нужен ли отдельный режим «high-precision only» (порог ≥ 0.95) для CSI-критичных подклассов `issue` | BA | возможное расширение требования |

## Бриф для SA

**Требование:** [content/30-requirements/functional/uc3-duplicate-detection.md](uc3-duplicate-detection.md)
**Фаза:** PoC

**Спроектировать:**

- Компонент **near-duplicate online** для сценария А: точка интеграции в SMP-форме регистрации `issue`, способ получения эмбеддинга регистрируемой заявки (ad-hoc через Yandex FM vs ленивая опора на UC1-джобу), API возврата кандидатов, ACL-фильтрация на уровне SMP.
- Компонент **batch duplicate-audit** для сценария Б: scheduled job (паттерн UC1-джобы), выбор алгоритма (cosine-threshold с группировкой пар как baseline; HDBSCAN+UMAP как резерв при росте объёмов / запросе на многоэлементные группы), формат и канал отчёта.
- Модель данных: где хранить cluster-метки или групповые идентификаторы (отдельная векторная таблица vs SMP-атрибут vs только в отчёте), как версионировать пороги и идентификатор модели эмбеддингов в записи отчёта (NFR-008 / AC-010).
- Контракт offline-evaluation: процедура воспроизводимого замера precision / recall на размеченном срезе по `issue.duplicates`.

**Бизнес-правила для валидаций:**

- BR-001 — никакого автомёрджа: архитектура **не имеет** записи в `issue.duplicates` / `issue.duplicatesRL` со стороны pg_vector_service в PoC.
- BR-003 / FR-005 — ACL SMP применяется до возврата кандидатов; обход через прямой доступ к векторной таблице запрещён (это уже зафиксировано как «доступ к БД только через SMP API» в CLAUDE.md).
- BR-004 / NFR-006 — в наружу (UI / отчёт) — только `subject` и метаданные; полный текст не покидает SMP-границу.
- BR-006 — embedding-вызовы ходят только по whitelist'у атрибутов из UC1; UC3 **не расширяет** периметр PII.

**Acceptance criteria для проверки архитектуры:**

- AC-003 (latency online) — обоснован выбор пути «ad-hoc embedding vs lazy» с оценкой бюджета.
- AC-006 / NFR-003 (batch window) — обоснован выбор алгоритма и его поведение при росте корпуса до миллиона объектов; чётко описан резервный путь (HDBSCAN+UMAP) на случай провала baseline.
- AC-008 (детерминированность) — описаны источники недетерминизма (если есть) и стратегия их фиксации (random_state / seed / порядок выгрузки).
- AC-010 (наблюдаемость) — в архитектуре зафиксировано хранение `embedding_model_id` и `thresholds` рядом с записью отчёта batch-аудита.

**Решения, которые нужно закрепить в ADR:**

- **ADR-YYY (алгоритм near-duplicate и пороги).** Финальные значения порогов `Дубль` / `Похожая`, выбор алгоритма для сценария А (cosine-threshold по KNN — рекомендация Researcher из `clustering-algos.md`).
- **ADR-YYY (алгоритм кластеризации для batch-аудита).** Cosine-threshold pairwise vs HDBSCAN+UMAP; критерии триггера резервного пути.
- **ADR-YYY (sync vs job-based vectorization для UC3 online).** Решение по Q7: ad-hoc embedding регистрируемой заявки vs lazy-зависимость от UC1-джобы.
