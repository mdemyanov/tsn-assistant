# ADR-003: Job-based vectorization (vs sync events)

**Status:** Draft
**Date:** 2026-05-01

## Context

Векторизация SMP-объектов перед записью в pgvector — единственный платный (с точки зрения YC FM-квоты) этап pipeline. Триггер для этого этапа может быть двух видов:

1. **Sync-векторизация** — action handler в SMP на событиях `afterAdd` / `afterModify` целевого объекта. Каждое создание/изменение whitelisted-атрибута немедленно вызывает YC FM, считает эмбеддинг и пишет вектор. Преимущество — нулевой дрейф; недостаток — нагрузка на YC FM пропорциональна потоку изменений в SMP, плюс задержка обработки события SMP блокируется внешним вызовом.
2. **Async-джоба** — `scheduledTask` SMP, запускающаяся по cron-расписанию; обрабатывает накопленные «грязные» объекты пакетами. Преимущество — изоляция нагрузки и контроль cost; недостаток — vector lag (вектор отстаёт от исходного объекта до момента следующего запуска джобы).

CLAUDE.md фиксирует выбранный приоритет PoC:

> Векторизация выбранных атрибутов SMP-объекта **джобой по расписанию** (sync-векторизация по событиям SMP — out of scope PoC).

То же продублировано в [UC1](../../30-requirements/functional/uc1-scheduled-vectorization):

- Описание: «фоновая массовая векторизация SMP-объектов: запускается по cron-расписанию, обрабатывает только те объекты, для которых вектор отсутствует или устарел».
- Раздел «Что НЕ входит»: «Sync-векторизация по событиям SMP (action handler на create/update/status-change) — отдельный сценарий, в PoC не реализуется».
- FR-001: «Джоба запускается планировщиком SMP (`scheduledTask`) по cron-подобному расписанию».

Дополнительные обоснования из [UC3](../../30-requirements/functional/uc3-duplicate-detection): online-сценарий А (подсказка дублей при регистрации заявки) ставит вопрос Q7 «ad-hoc embedding регистрируемой заявки vs lazy-зависимость от UC1-джобы» — этот вопрос **не решается** данным ADR; он касается единичного запроса в UC3 и закрепится в отдельном ADR при проектировании UC3.

Технические вводные:

- `api.scheduler` (см. `content/10-domain/research/smp-scheduled-jobs.md`): поддерживает cron-подобное расписание, ручной запуск, прерывание (`interruptJob` через Thread Death). Strategy `from_start` / `from_last_execution`.
- `api.tx.call()` — обёртка для атомарности батча (NFR-023).
- YC FM-квоты на embedding-RPS неизвестны (RES-002 OQ-5, заблокирован CAPTCHA на момент BA); пиковый поток создания заявок в SMP может многократно превышать sustained RPS YC FM. Sync-режим в этом случае — DDoS на YC FM, который выльется в 429-ошибки на регистрации заявок.

## Decision

**Векторизация SMP-объектов в PoC выполняется через `scheduledTask` SMP по расписанию (job-based, async).** Sync-векторизация через action handler (`afterAdd` / `afterModify`) — out of scope PoC.

**Принципы реализации:**

- Один `scheduledTask` `pg_vector_service__vectorize_job` с конфигурируемым cron-расписанием (UC1 FR-001). Расписание настраивает админ стенда через UI планировщика SMP без правок кода.
- Адаптер `adapters/scheduler/` (по ADR-001) — единственная точка входа в `core/` от scheduler'а; реализует `SchedulerEntryPort`.
- Признак «пора пересчитать» — атрибут `vector_dirty` (или эквивалентный, конкретный механизм — отдельный ADR по UC1 FR-007: атрибут SMP / mtime-сравнение / staging-таблица). Атомарность сброса `vector_dirty = false` одновременно с записью вектора (NFR-UC1-004) обеспечивается обёрткой `api.tx.call()` вокруг батча (NFR-023).
- Идемпотентность (NFR-020 / UC1 FR-008): повторный запуск на неизменённом snapshot'е и неизменённой версии модели — не делает ни одного платного вызова YC FM.
- Lock против concurrent-runs (UC1 FR-015): новый запуск пропускается, если предыдущий не завершился (детектируется по статусу `scheduledTask` или платформенному lock'у — конкретный механизм — отдельный ADR).
- Дрейф «момент изменения объекта → момент пересчёта вектора» — **допустим**. Численный потолок дрейфа (минуты / часы) — **open question** (UC1 OQ-UC1-2: расписание по умолчанию для PoC; зависит от owner-гейтов).

**Что НЕ закрывает данный ADR (предмет отдельных ADR):**

- Конкретный cron-расписания для PoC (FR-001) — настраивается админом, дефолт фиксируется в config-ADR.
- Механизм dirty-tracking (FR-007) — отдельный ADR по UC1.
- Retry-policy для YC FM (FR-012, NFR-021) — отдельный ADR.
- Job locking и time-budget (FR-015, FR-016) — отдельный ADR.
- Online-сценарий ad-hoc embedding для UC3 А (Q7) — решается в проектировании UC3, не противоречит данному ADR (UC3 А — read-side, не пишет в pgvector).
- Возможный переход на sync-режим после PoC — требует **нового ADR** с явным supersede-указанием на этот.

## Consequences

**Positive:**

- **Изоляция нагрузки на YC FM:** при пиковом потоке регистрации заявок (UC3 NFR-002) векторизация не создаёт отдельной нагрузки — она «размазывается» по расписанию джобы. RPS YC FM ограничен размером батча и частотой запуска, а не реальным потоком SMP-изменений.
- **Контроль cost (NFR-061 / UC1 NFR-UC1-002):** дневной потолок токенов / ₽ предсказуем — задаётся произведением «частота запуска × размер батча × число whitelisted-объектов на запуск». Sync-режим этой предсказуемостью не обладает.
- **Batch-эффективность:** при наличии у YC FM batch-API (RES-002 OQ-3, заблокирован) можно отправлять группу текстов одним вызовом, уменьшая overhead на каждый объект.
- **Проще recovery:** если YC FM недоступен в момент изменения объекта, в sync-режиме приходится либо ставить event в очередь, либо терять обновление; в job-режиме объект просто остаётся `dirty` и попадает в следующий запуск (UC1 FR-012 / NFR-021).
- **Соответствует SMP-паттерну:** `scheduledTask` — стандартный механизм SMP для batch-операций; админ стенда управляет им штатным UI (UC1 AC-001).

**Negative:**

- **Vector lag:** между изменением SMP-объекта и появлением актуального вектора в pgvector — окно длительностью N (равно периоду расписания + время выполнения джобы). UC2 (similarity-поиск) при этом возвращает результаты по **устаревшим** векторам. Open question: насколько долгий lag допустим (зависит от UC1 OQ-UC1-2 и SLA).
- **«Холодный старт» для новых объектов:** до первого прогона джобы новые объекты не векторизованы. UC2 / UC3 должны корректно обрабатывать кейс «вектор не найден» (UC2 FR-010 / AC-9, UC3 FR-008 / BR-005).
- **UC3 online-сценарий частично deferred:** подсказка дублей при регистрации заявки требует embedding **до** того, как джоба отработает на новой заявке. Решение по Q7 (`UC3`) либо ad-hoc YC FM-вызов в момент регистрации (один объект, не batch), либо silent skip при отсутствии вектора. Обе опции совместимы с этим ADR — он не запрещает single-shot вызов из online-кода.
- **Сложнее dirty-tracking:** в sync-режиме выставление маркера `dirty` — побочный эффект action handler'а; в job-режиме нужно явно ловить событие изменения whitelisted-атрибута и проставлять `vector_dirty = true`. Это open question (UC1 FR-007).

**Mitigations:**

- **Документация ожиданий по freshness:** в архитектурной статье `content/40-architecture/` фиксируется явное предложение для UC2/UC3: «freshness ≤ N часов; для UC2 это означает, что заявки моложе N часов могут отсутствовать в выдаче». Точное N — после OQ-UC1-2.
- **Атомарный dirty-flag:** механизм выставления `vector_dirty` (отдельный ADR по UC1 FR-007) обеспечивает eventual consistency: ни одно изменение whitelisted-атрибута не теряется, даже если джоба упала.
- **Метрика lag-а:** включается в реестр метрик NFR-050 — `vector_age_p95` (распределение «возраст актуального вектора относительно `mtime` исходного объекта»). Помогает калибровать расписание.
- **Путь к sync-режиму после PoC:** не закрыт. После замеров на стенде `llm2` (UC2 NFR-001 latency, UC3 NFR-001 online latency) можно принять отдельный ADR с переходом части классов на sync (например, `issue` для UC3 online), оставив остальные на job-режиме. Этот ADR не предрешает миграцию, но и не блокирует её.

## Alternatives Considered

- **Sync через action handler (`afterAdd` / `afterModify`):** триггер на каждое изменение whitelisted-атрибута; немедленный YC FM-вызов; запись вектора в pgvector в той же транзакции (или в follow-up асинхронной). Отвергнуто для PoC по двум причинам:
    1. Перегрузка YC FM при пиковом потоке заявок (UC3 NFR-002) — без известной RPS-квоты YC FM (RES-002 OQ-5) гарантировать стабильность невозможно. 429-ошибки на регистрации заявок недопустимы для оператора Service Desk.
    2. Платформенная блокировка: вызов из action handler в `afterAdd` блокирует commit транзакции SMP до возврата YC FM (или до taймаута). Это деградирует p95 регистрации заявок (NFR-UC1-003 в UC1 — «не должна заметно деградировать отклик SMP»).
- **Гибрид:** sync для критичных классов (`issue` — для UC3 online), async для остальных (`knowledgeBase`, `problem`). Отвергнуто **на этапе PoC**: усложняет архитектуру, требует двух code path'ов. После PoC — рассматривается отдельным ADR.
- **Pull-based на стороне UC2/UC3** (lazy-векторизация в момент запроса): оставить pgvector только для уже посчитанных, в момент запроса проверять «есть ли вектор? если нет — посчитать на лету и сохранить». Отвергнуто — это де-факто online-sync со сложным кешированием; ломает идемпотентность (UC1 NFR-020), создаёт race conditions при concurrent-запросах на один объект.
