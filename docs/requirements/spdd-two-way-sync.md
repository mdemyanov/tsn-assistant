# BA-001 Two-way sync — правило обновления слоёв

## JTBD

Когда PM или автор контента обнаруживает расхождение между вышестоящим и нижестоящим слоями проекта, я (PM шаблона project_template) хочу иметь явное правило «сначала обнови вышестоящий слой», чтобы нижестоящий слой всегда оставался синхронизированным и /pm-review мог механически проверить порядок обновлений.

## Контекст и мотивация

SPDD (Thoughtworks, апрель 2026) формулирует принцип двусторонней синхронизации: при любом расхождении между слоями — сначала фиксируется вышестоящий слой (требования, архитектура, принципы), потом обновляется нижестоящий (реализация, runbook, playbook). Шаблон project_template уже реализует этот поток как процесс через pipeline PM→BA→SA→Dev, но правило нигде не зафиксировано явно и не проверяется автоматически.

Шаблон поддерживает 7 профилей: project, product, kb-team, kb-product, methodology, course, custom. Четыре из них — content-only (kb-team, kb-product, methodology, course), не используют `src/`. Правило формулируется универсально: «вышестоящий слой → нижестоящий слой» без привязки к конкретным каталогам. Конкретные пары для профиля хранятся в `manifest.yaml` каждого профиля, поле `drift_pairs`.

Источник принципа: [SPDD — ключевые принципы](../10-domain/spdd-key-principles) (RES-001), цитата: «Когда реальность расходится — сначала исправь промпт, потом обнови код».

## Функциональные требования

- **FR-001:** В `CLAUDE.md` шаблона должен появиться отдельный раздел «Правило two-way sync» с универсальной формулировкой: при расхождении любого нижестоящего слоя с вышестоящим — сначала обновляется вышестоящий, затем нижестоящий.
- **FR-002:** Раздел должен содержать таблицу примеров пар upstream → downstream для всех 7 профилей (значения из `drift_pairs` манифестов).
- **FR-003:** Раздел должен указывать, что единственное допустимое исключение — hotfix на production: в этом случае вышестоящий слой обновляется post-mortem сразу после фикса, а не вместо него.
- **FR-004:** В разделе «Красные линии» `CLAUDE.md` должна появиться строка: «расхождение нижестоящего слоя с вышестоящим без предшествующего обновления вышестоящего — блокер для /pm-review».
- **FR-005:** `README.md` шаблона должен содержать короткий pointer (1-2 предложения) на раздел `CLAUDE.md§two-way-sync` для читателей, не открывающих полный `CLAUDE.md`.

## Нефункциональные требования

- **NFR-001:** Раздел `CLAUDE.md` — не более 30 строк. Деталь (таблица примеров) вынесена в тело раздела, не рассеяна по другим секциям.
- **NFR-002:** Формулировка правила не использует термины `src/`, `код`, `спека` как единственные примеры — только «вышестоящий слой» / «нижестоящий слой» в основном тексте; конкретные примеры — в таблице профилей.
- **NFR-003:** Изменения в `CLAUDE.md` backward-compatible: существующие проекты без `drift_pairs` в manifest не получают ошибок — только INFO-skip.

## User Journey

**Автор контента обнаружил расхождение:**
1. Автор замечает: нижестоящий слой (например, `content/60-implementation/`) изменился, а вышестоящий (`content/30-requirements/`) — нет.
2. Автор читает `CLAUDE.md§two-way-sync` или README pointer.
3. Автор обновляет вышестоящий слой (требование, архитектуру, принципы) — commit.
4. Автор обновляет нижестоящий слой — отдельный commit или продолжение работы.
5. /pm-review видит оба обновления, drift-check чистый.

**Hotfix-исключение:**
1. Критический баг на production, нет времени обновлять требования.
2. Hotfix коммитится напрямую в нижестоящий слой.
3. В commit message — trailer `skip-drift: hotfix — <описание>`.
4. Сразу после фикса автор открывает вышестоящий слой и вносит post-mortem обновление.
5. /pm-review видит bypass-trailer, выдаёт INFO вместо WARN.

**Альтернативный путь — escalation:**
Если автор не уверен, что именно нужно менять в вышестоящем слое, — эскалирует к BA/PO на шаге 2 (до обновления нижестоящего). Это явное требование SPDD: эскалация происходит до генерации/обновления, а не после.

## Бизнес-правила

- **BR-001:** Нижестоящий слой не может быть обновлён в PR-ветке без соответствующего обновления вышестоящего слоя в той же ветке — если только не указан bypass-trailer `skip-drift: <reason>`.
- **BR-002:** Hotfix — единственное исключение из BR-001. Post-mortem обновление вышестоящего слоя обязательно и должно последовать не позднее следующего рабочего цикла.
- **BR-003:** Bypass-trailer `skip-drift: <reason>` должен содержать явное обоснование (не пустую строку). Приемлемые значения: `hotfix`, `refactoring only`, `docs only` с кратким пояснением.
- **BR-004:** Правило применяется в момент обнаружения расхождения, а не откладывается. Escalation к BA/PO — до обновления нижестоящего слоя.

## Доменные события

- Расхождение обнаружено → автор обновляет вышестоящий слой (требование/архитектуру/принцип)
- Вышестоящий слой обновлён → автор обновляет нижестоящий слой
- Hotfix выполнен → автор добавляет bypass-trailer + планирует post-mortem обновление upstream
- /pm-review запущен → drift-check читает `drift_pairs`, сравнивает diff private vs public

## Acceptance Criteria

- [ ] **AC-001:** В `CLAUDE.md` шаблона существует раздел с заголовком «Правило two-way sync» (или аналогичным), содержащий формулировку принципа «вышестоящий слой обновляется первым».
- [ ] **AC-002:** Раздел содержит таблицу или список примеров пар upstream→downstream для не менее чем 5 из 7 профилей (включая минимум 2 content-only профиля).
- [ ] **AC-003:** Раздел явно описывает исключение «hotfix на production»: вышестоящий слой обновляется post-mortem, bypass-trailer `skip-drift: hotfix` допустим.
- [ ] **AC-004:** В разделе «Красные линии» `CLAUDE.md` есть строка, указывающая, что расхождение без обновления upstream — блокер для /pm-review.
- [ ] **AC-005:** `README.md` содержит pointer на раздел two-way sync в `CLAUDE.md` (1-2 предложения, с якорной ссылкой или упоминанием раздела).
- [ ] **AC-006:** Существующий проект без `drift_pairs` в manifest не получает ошибок при запуске /pm-review — только INFO-skip.
- [ ] **AC-007:** Тест `scripts/tests/test_two_way_sync_in_claude_md.py` проходит зелёным (проверяет наличие ключевых ключевых слов раздела в `CLAUDE.md`).

## Инварианты и Safeguards

**Содержательные:**
- Правило обязано охватывать все 7 профилей, включая content-only — ни один профиль не является исключением из принципа two-way sync.
- Единственное исключение из правила — hotfix; любые другие bypass без явного обоснования недопустимы.
- Escalation к BA/PO происходит до обновления нижестоящего слоя, не после.

**Sensitive content:**
- В примерах пар не использовать реальные имена проектов, клиентов или сотрудников.
- `CLAUDE.md` и `README.md` не должны содержать API-ключей, токенов, credentials даже в примерах.

**Жизненный цикл:**
- Owner: BA → SA (при проектировании drift-check) → Dev (при реализации).
- Дата следующей ревизии: после завершения SA-001 и review ADR-004.
- При появлении новых профилей в шаблоне — таблица пар в `CLAUDE.md` должна быть обновлена.
