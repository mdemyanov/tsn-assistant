# UC-S3 — Поиск похожего вопроса (FAQ-сценарий)

> **Новый UC.** Выделен из UC-S1 как отдельный сценарий с принципиально иным payload: короткий вопрос пользователя (10–50 слов) → поиск в каталоге «частых вопросов» с готовым ответом. Ключевой вопрос по классу FAQ-объектов — owner-decision (OQ-FAQ).
>
> **BA-003 (2026-05-01):** применён BA-003-M1 (scope narrowing). JTBD-2 (self-service портал) и JTBD-3 (чат-бот) **явно выведены за рамки PoC** — см. секцию ниже. PoC реализует только JTBD-1 (оператор Service Desk, подсказка на форме регистрации). Добавлен OQ-S3-4 (минимальный объём FAQ для обоснования vector vs keyword). Трассируемость: старые AC-001..008 сохранены без изменений; AC специфичные для JTBD-2/3 явно помечены «out of PoC scope».

## Описание

UC-S3 — семантический поиск в каталоге FAQ-записей. Запрос — короткий текст (10–50 слов) пользователя. Ответ — top-K FAQ-вопросов с их эталонными ответами, ранжированных по cosine similarity.

**В PoC реализуется только Journey-1 (JTBD-1): оператор видит подсказку на форме регистрации заявки.** Journey-2 и Journey-3 — deferred.

**Принципиальное отличие от UC-S1:**
- Запрос всегда free-text (тип `text-search-query`), никогда не «по объекту».
- Целевые объекты — короткие FAQ-записи (не длинные заявки/KB-статьи).
- Ответ содержит готовый текст ответа (или ссылку на него).
- Применяется порог релевантности (cutoff): записи ниже порога не показываются.

**Неопределённость по классу FAQ-объектов.** Owner должен решить: отдельный SMP-класс `faq$question` или признак `type=question` на `knowledgeBase$article` (OQ-FAQ). До решения UC-S3 описывает оба варианта.

**Модель эмбеддинга.** Для векторизации FAQ-вопросов при индексации — `text-search-doc`. Для запроса пользователя — `text-search-query` (асимметричная пара, ADR-010).

## Функциональные требования

- **FR-001. Поиск по тексту запроса.** Принимает `{text, K, score_threshold}`. Формирует embedding через `text-search-query`, ищет в FAQ-векторах по cosine similarity. **Pre-condition (Resolved OQ-S3-4, 2026-05-02):** vector search в UC-S3 оправдан при наличии ≥ 50 активных FAQ-записей; при меньшем объёме рекомендуется BM25/keyword.
- **FR-002. Cutoff threshold.** Записи с `score < score_threshold` в выдачу не попадают. Default threshold — открытый вопрос (OQ-S3-1); черновое значение — 0.75 (для асимметричных моделей).
- **FR-003. Параметр K.** Default = 5. Диапазон ≤ 20 (FAQ-сценарий — короткий список, иначе теряет смысл).
- **FR-004. Поля в ответе.** Каждая запись: `faq_id`, `question_text` (превью), `answer_text` или `answer_url`, `score`.
- **FR-005. Фильтр активных FAQ-записей.** Поиск ведётся только по FAQ-записям в статусе «активно» / «опубликовано». Архивные FAQ-записи в выдаче не появляются.
- **FR-006. ACL FAQ.** Если FAQ-класс реализован через `knowledgeBase$article` — применяется `kbAccesses` (BR-002). Если отдельный класс — ACL определяется при реализации (OQ-FAQ).
- **FR-007. Ошибки.** При отсутствии FAQ-векторов — `FaqVectorsNotAvailable`. Структура без stack-trace.
- **FR-008. Логирование.** `correlationId`, длина запроса (не текст), K, threshold, `latencyMs`, `resultCount`.

## Нефункциональные требования

- **NFR-S3-001. Latency p95.** Короткий текст (≤ 50 слов) → быстрый embedding. Ожидаемый бюджет — как UC-S1 (≤ 500 ms). Финальный — после smoke.
- **NFR-S3-002. Качество (черновой).** Precision@5 ≥ 0.80 при threshold=0.75. Оценивается на размеченном наборе «вопрос → правильный FAQ». Финальные пороги — после offline-eval с реальными FAQ-данными.
- **NFR-S3-003. Предсказуемость пустого результата.** При отсутствии подходящих FAQ (все записи ниже threshold) — пустой список, не ошибка. UI должен корректно показать «FAQ не найден».
- **NFR-S3-004. Тенант-изоляция.** FAQ другого тенанта не попадают в выдачу.

## User Journey

### Journey-1. Оператор — подсказка на форме регистрации (PoC scope)

1. Оператор начинает заполнять поле `subject` заявки: «не открывается VPN после обновления».
2. UI (по debounce) вызывает UC-S3: `{text='не открывается VPN после обновления', K=5, threshold=0.75}`.
3. UC-S3 строит embedding через `text-search-query`, ищет в FAQ.
4. Возвращаются 5 записей с `question_text`, `answer_text`, `score`.
5. UI показывает блок «Возможные ответы из FAQ» — оператор зачитывает заявителю или предлагает ссылку.
6. Если заявитель подтверждает «это помогло» — оператор закрывает заявку с типом «решено по FAQ».

**Альтернатива:** ни одна FAQ-запись не набрала порог → блок скрывается, оператор продолжает регистрацию.

### Journey-2. Заявитель — self-service портал (Deferred — MVP/Pilot scope)

> **Out of PoC scope.** Описание сохранено для будущей фазы.

1. Заявитель вводит в строку поиска: «сброс пароля».
2. Портал вызывает UC-S3: `{text='сброс пароля', K=5}`.
3. Возвращаются FAQ-записи с инструкцией.
4. Заявитель следует инструкции — проблема решена без заявки.

### Journey-3. Чат-бот — suggested answer (Deferred — MVP/Pilot scope)

> **Out of PoC scope.** Описание сохранено для будущей фазы. Auto-answer при score ≥ 0.90 — явно MVP/Pilot.

1. Пользователь пишет боту: «как подключить VPN из дома».
2. Бот вызывает UC-S3: `{text='как подключить VPN из дома', K=3, threshold=0.80}`.
3. Если max_score ≥ 0.90 — бот автоматически отправляет `answer_text` пользователю.
4. Если 0.80 ≤ max_score < 0.90 — бот предлагает список FAQ-вариантов.
5. Если score < 0.80 — бот направляет на оператора.

## Бизнес-правила

- **BR-001. Отдельная FAQ-коллекция.** FAQ-объекты хранят vectorized в отдельном logical-namespace (meta_class = `faq$question` или `knowledgeBase$article` с `type=question`). Поиск UC-S3 ведётся только в этом namespace.
- **BR-002. kbAccesses для KB-вариант.** Если FAQ реализован через `knowledgeBase$article`, применяется `kbAccesses`-фильтр (аналогично UC-S1 BR-002).
- **BR-003. Cutoff обязателен.** Ниже порога — не показывать. UC-S3 не должен выдавать «что угодно лишь бы что-то показать» — пустой список лучше нерелевантного ответа.
- **BR-004. PII в логах.** Текст запроса не логируется (BR-003 из UC-S1 / CLAUDE.md).
- **BR-005. Только активные FAQ.** Архивные / неопубликованные записи исключены из индекса или из выдачи (FR-005).

## Доменные события

- **FaqSearchRequested** (`K`, `threshold`, `correlationId`) — запрос принят.
- **FaqSearchCompleted** (`correlationId`, `resultCount`, `latencyMs`) — запрос обработан.
- **FaqSearchFailed** (`correlationId`, `errorCode`) — ошибка.

### Pros/cons для OQ-FAQ

**Вариант A — отдельный класс `faq$question`:**
- Pros: чистая модель, отдельный ACL, нет смешения с KB-статьями, легко расширять атрибуты (rating, source).
- Cons: требует конфигурирования нового FQN-класса в SMP (work для DevOps/Сахабетдинов), отдельная настройка `kbAccesses` если нужна.

**Вариант B — `knowledgeBase$article` с `type=question`:**
- Pros: переиспользует существующую инфраструктуру KB, не требует нового SMP-класса, ACL через `kbAccesses` работает сразу.
- Cons: смешивает FAQ с обычными KB-статьями, фильтрация по `type` нужна везде, поиск UC-S1 / UC-S4 нужно явно исключать FAQ из выдачи (или включать — неоднозначно).

**Рекомендация BA (не решение):** при наличии возможности создать новый класс в SMP — вариант A предпочтителен ради чистоты модели. Если создание класса занимает > 1 дня — вариант B для PoC с планом миграции на A в MVP.
