# UC-C2 — Кластеризация заявок по описанию + комментариям (combined signal)

> **Новый UC.** Расширение UC-C1: добавляет сигнал comment-векторов к атрибутному. Зависит от UC-V2. Реализуется после sign-off на `comment.text` (OQ-V2-1).

## Описание

UC-C2 — кластеризация на основе **combined signal**: атрибутного вектора (UC-V1) + агрегата comment-векторов (UC-V2).

**Бизнес-гипотеза:** две заявки с разным первоначальным описанием («не работает VPN» vs «нет доступа к корпоративным ресурсам»), но с одинаковым обнаруженным root cause в переписке, окажутся в одном кластере UC-C2, но не в UC-C1.

**Два сигнала:**
1. `issue_vector` — composite_extended (UC-V1), `chunk_kind='object'`
2. `comment_aggregate` — агрегат comment-векторов заявки (max-similarity или mean из top-N комментариев), `chunk_kind='related'`

**Вес сигналов:** базовое значение `w1=0.5, w2=0.5` (50/50). Resolved OQ-CL-1 (2026-05-02): Owner: Демьянов. Финальная калибровка — offline-eval post-MVP (DEV-033/034). До offline-eval веса варьируются как гиперпараметр.

**Fallback для заявок без комментариев:** если у заявки нет comment-векторов — используется только `issue_vector` (вырождается в UC-C1 для этой заявки). Смешанная выборка (с комментариями + без) допустима в одном отчёте.

**Зависимость от UC-V2:** активируется только при `comment_vectorization.enabled=true`.

## Функциональные требования

- **FR-001. Batch-режим (primary).** Еженедельная джоба выгружает combined signal для `issue` за окно и формирует группы.
- **FR-002. Combined similarity.** Для пары заявок `(I_a, I_b)`: `combined_score = w1 × cosine(issue_a, issue_b) + w2 × cosine(comment_agg_a, comment_agg_b)`, где `w1 + w2 = 1.0`, **default `w1=0.5, w2=0.5`** (calibrate post-MVP offline-eval, OQ-CL-1 Resolved). Веса — конфигурируемы без перекомпиляции JAR.
- **FR-003. Fallback для заявок без комментариев.** Если у заявки `I_x` нет comment-векторов: `comment_agg_x = null`, `combined_score = cosine(issue_a, issue_b)` (только issue-сигнал). Заявки без комментариев участвуют в кластеризации через issue-сигнал.
- **FR-004. Агрегация comment-векторов.** Для одной заявки с N комментариями: агрегат = max-similarity (OQ-CL-2 Resolved, аналогично UC-S2) или mean-pool. Default = mean-pool всех comment-векторов заявки (с cap по FR-005). Метод агрегации конфигурируем.
- **FR-005. Cap на комментарии.** В агрегат входят не более `comment.cap` последних комментариев (default=50, наследуется от UC-V2 FR-008). Аномальная заявка с 8 248 комментариями не порождает 8k-размерный агрегат.
- **FR-006. Выход отчёта.** Группы near-duplicate; для каждой: список объектов, `combined_score`, `issue_score`, `comment_score`, тип, `subject`, метка known/new.
- **FR-007. Пометка known-групп.** Группы, покрытые `issue.duplicates` / `issue.duplicatesRL`, помечаются «известные» (аналогично UC-C1 FR-011).
- **FR-008. Никакого автомёрджа.** Джоба только формирует отчёт.
- **FR-009. ACL.** Заявки, к которым у получателя отчёта нет доступа, в отчёт не включаются.
- **FR-010. Логирование.** Размер выборки, число групп, число known, `w1`/`w2`, версия модели, пороги, длительность.

## Нефункциональные требования

- **NFR-C2-001. Batch window.** Как UC-C1 (NFR-C1-002): ≤ 4 ч при сотнях тысяч объектов. Combined signal увеличивает объём данных на memory, но не на YC FM-вызовы (векторы уже посчитаны).
- **NFR-C2-002. Зависимость от UC-V2.** Без comment-векторов UC-C2 вырождается в UC-C1. Аналитик должен явно видеть в отчёте, у скольких заявок использован combined signal, а у скольких — только issue-signal (FR-006).
- **NFR-C2-003. Детерминированность.** При фиксированных `w1`, `w2`, алгоритме агрегации и algorithm_version — повторный запуск на тех же данных даёт сопоставимые группы.
- **NFR-C2-004. Тенант-изоляция.** Только объекты текущего тенанта.

## User Journey

### Сценарий — batch-аудит (happy path)

1. Джоба `cluster-combined-audit` запускается по расписанию.
2. Для каждой `issue` за окно: загрузка `issue_vector` (chunk_kind='object') + агрегация comment-векторов (top-cap, mean-pool).
3. Расчёт pairwise combined_score для всех пар (или выборки).
4. Группировка по порогу (cosine-threshold baseline / HDBSCAN+UMAP резерв).
5. Пометка known-групп.
6. Формирование отчёта: группы + breakdown (combined / issue-only / comment-only signal).
7. Публикация аналитику.

**Альтернатива:** превышение batch window → аварийная остановка, без частичного отчёта.

**Альтернатива: UC-V2 не активирован.** Джоба UC-C2 работает в режиме UC-C1 (только issue-сигнал) с явной пометкой в отчёте «comment_vectorization.enabled=false, fallback to issue-only».

## Бизнес-правила

- **BR-001. Никакого автомёрджа.** Аналогично UC-C1.
- **BR-002. Fallback явный.** В отчёте явно отражается, какие заявки использовали combined signal, а какие — только issue-signal (BR-002 из UC-C1).
- **BR-003. Веса — конфигурируемые.** `w1` и `w2` не захардкожены, версионируются как часть конфигурации отчёта.
- **BR-004. Cap на комментарии обязателен.** Наследуется от UC-V2 BR-004.
- **BR-005. Только user-комментарии.** Наследуется от UC-V2 BR-002 (система-комментарии фильтруются).
- **BR-006. Whitelist — только из UC-V1 и UC-V2.** UC-C2 не расширяет периметр PII.

## Доменные события

- **CombinedClusterAuditStarted** — джоба стартовала; `w1`, `w2`, `comment_cap`, версия модели.
- **CombinedClusterAuditCompleted** — завершилась; число групп, процент заявок с comment-signal, длительность.
- **CombinedClusterAuditFailed** — не уложилась в окно.

## Acceptance Criteria

- [ ] **AC-001.** Batch-отчёт UC-C2 содержит ≥ 1 группу, в которой хотя бы у одной заявки использован combined signal (есть comment-векторы).
- [ ] **AC-002.** Заявки без comment-векторов участвуют через issue-signal (fallback, FR-003); в отчёте они явно помечены «issue-only signal».
- [ ] **AC-003.** Изменение `w1`/`w2` приводит к изменению состава групп (или по крайней мере combined_score) без перекомпиляции JAR.
- [ ] **AC-004.** Группы с аномальной заявкой (8 248 комментариев) не включают более `comment.cap` комментариев в агрегат (FR-005, BR-004).
- [ ] **AC-005.** Отчёт не содержит объектов без ACL у получателя (FR-009, BR-006).
- [ ] **AC-006. UC-V2 не активирован.** Джоба работает в режиме fallback (issue-only), отчёт содержит пометку «comment signal недоступен».
- [ ] **AC-007.** Лог запуска содержит `w1`, `w2`, `comment_cap`, версию модели, число заявок с comment-signal (NFR-C2-003, FR-010).
- [ ] **AC-008.** Повторный запуск на тех же данных с теми же параметрами → сопоставимые группы (детерминированность).

### Pros/cons для OQ-CL-1 (веса)

**50/50:**
- Pros: KISS, симметричный сигнал, стартовая точка для eval.
- Cons: comment-signal слабее при небольшом числе комментариев (median 3); может занижать combined_score.

**70/30 (issue=70, comment=30):**
- Pros: issue-сигнал более надёжен (всегда есть, стабильный composite), comment — дополнительный сигнал.
- Cons: comment-сигнал влияет меньше, UC-C2 ближе к UC-C1.

**Learnable (по данным offline-eval):**
- Pros: оптимальное соотношение.
- Cons: требует размеченного датасета с combined-ground truth (которого на llm2 нет).

**Рекомендация BA:** начать с 50/50, сравнить quality с UC-C1 на offline-eval; если combined signal не улучшает Precision@T — переключиться на 70/30 или свернуть UC-C2 до MVP.

## Бриф для SA

**Требование:** `content/30-requirements/functional/uc-c2-cluster-by-description-comments.md`
**Фаза:** PoC

**Спроектировать:**
- Combined-similarity вычисление: weighted sum `w1 × issue_cosine + w2 × comment_agg_cosine`. Как получить `comment_agg_vector` для заявки (загрузить все comment-строки по `parent_id`, mean-pool).
- SQL-паттерн: для каждой `issue` — LEFT JOIN на comment-векторы по `parent_id` (GROUP BY mean), NULL если нет комментариев → fallback.
- Конфигурируемые веса `w1`, `w2` — part of report config / ADR.
- Алгоритм кластеризации (OQ-CL-4): cosine-threshold baseline → HDBSCAN+UMAP резерв.
- Feature-flag: UC-C2 активируется при `comment_vectorization.enabled=true`; иначе — fallback UC-C1.

**Бизнес-правила для валидаций:** BR-001 (нет автомёрджа), BR-002 (явный fallback), BR-003 (веса конфигурируемы), BR-004 (cap), BR-005 (только user-комментарии).

**AC для проверки архитектуры:** AC-003 (смена весов без перекомпиляции), AC-004 (cap соблюдается), AC-006 (feature-flag поведение).

**Решения по OQ-CL-1 и OQ-CL-2 закрепляются в ADR** после offline-eval (DEV-033/034).
