# UC-V2 — Векторизация комментариев SMP-объектов

> **Новый UC.** Выделен из UC-V1 как самостоятельный payload-класс. Комментарии имеют отдельный жизненный цикл, ACL-модель и распределение длин, принципиально отличные от атрибутных полей.
>
> **Статус реализации в PoC (обновлено 2026-05-02):** Sign-off owner'а на `comment.text` получен (Resolved OQ-V2-1). DDL-поддержка (`parent_id`, `chunk_kind='related'`) закладывается в ADR-011. Пайплайн UC-V2 реализуется в PoC. Дополнительно создан OQ-V2-5: PII-mask preprocessing — defer to MVP.

## Описание

UC-V2 — векторизация текстов комментариев (`comment.text`) SMP-объектов. Это самостоятельный payload-класс с отдельной политикой хранения, ACL и lifecycle.

**Чем отличается от UC-V1:**

| Параметр | UC-V1 (атрибуты) | UC-V2 (комментарии) |
|---|---|---|
| Payload | composite-текст атрибутов объекта | текст одного комментария |
| Lifecycle | меняется вместе с объектом | комментарий создаётся / редактируется / удаляется независимо |
| Размер | p95 = 209 ток. (issue.composite_extended) | p95 = 2 432 ток. (7 % > 2 048 → chunking для части) |
| Cardinalily | 1 вектор на объект | N векторов на объект (median 3, p95 15, max 8 248) |
| ACL | у issue/problem нет per-object ACL | наследуется от объекта-родителя |
| Storage | `chunk_kind = 'object'` | `chunk_kind = 'related'`, `parent_id = issue.id` |

**Аномалия:** на стенде `llm2` есть 1 объект с 8 248 комментариями. Caller **обязан** применять cap (не передавать более N комментариев в одном вызове) — без cap один объект породит 8k+ вызовов YC FM.

**Статус в PoC (обновлено 2026-05-02):** Sign-off owner'а получен (Resolved OQ-V2-1). DDL-поддержка закладывается в ADR-011. Пайплайн реализуется в PoC.

**Фильтр system-комментариев.** Caller должен фильтровать автоматически созданные комментарии (смена статуса, системные уведомления) по признаку `comment.source.metaClass`. Точный список метаклассов для фильтрации — открытый вопрос (OQ-V2-2, адресат: SA / Сахабетдинов).

### Что НЕ входит

- Векторизация атрибутов объекта — UC-V1.
- Similarity-поиск по комментариям — UC-S2.
- Кластеризация с учётом комментариев — UC-C2.
- Авто-удаление/обновление векторов при изменении комментариев без участия caller'а — out of scope модуля (caller инициирует операцию).

## Функциональные требования

- **FR-001. Векторизация одного комментария.** Модуль принимает от caller'а `{comment_id, parent_id, parent_meta_class, text}` и возвращает vectorId. Поле `text` — значение `comment.text` после preprocessing по политике из `content/30-requirements/non-functional/nfr-preprocessing.md`.
- **FR-002. Chunking для длинных комментариев.** Если `comment.text` превышает лимит модели (7 % комментариев, p95 = 2 432 ток.), текст чанкируется с теми же параметрами что и KB в UC-V1: chunk_size=1 800 ток., overlap=10 %. Результат — N строк с `parent_id = comment_id` (или `object_id = comment_id`, `chunk_index = 1,2,...`).
- **FR-003. ACL-наследование.** ACL вектора комментария наследуется от объекта-родителя (`parent_id`). При поиске UC-S2 фильтрация идёт по ACL родительского объекта, а не по ACL комментария. Проверка доступа реализуется на уровне SMP API (BR-001).
- **FR-004. Удаление вектора при удалении комментария.** Когда caller удаляет комментарий, он вызывает метод `deleteCommentVector(comment_id)`. Способ детекции удаления — **SMP-event trigger (асинхронно)** (Resolved OQ-COMMENT-DELETE, 2026-05-02). Не GC. Детали реализации — в ADR. Owner: Демьянов.
- **FR-005. Re-vectorize при редактировании.** При редактировании `comment.text` — **SMP-event trigger (асинхронно)** инициирует пересчёт (Resolved OQ-COMMENT-EDIT, 2026-05-02). Не `dirty`-флаг через scheduled-scan. composite_hash изменяется → вектор пересчитывается при обработке события. Детали — в ADR.
- **FR-006. Фильтр system-комментариев.** Caller фильтрует автоматические комментарии (смена статуса, SLA-уведомления) по `comment.source.metaClass` перед передачей в модуль. Список отфильтровываемых метаклассов фиксируется в конфигурации whitelist'а как `comment.source.excluded_meta_classes`.
- **FR-007. Идемпотентность.** Ключ идемпотентности: `sha256(normalized_comment_text + model_version + whitelist_version + chunk_size + overlap + algorithm_version)`. Повторная передача неизменённого комментария → 0 вызовов YC FM.
- **FR-008. Cap на количество комментариев.** Caller должен ограничивать число передаваемых комментариев на один parent-объект. Рекомендуемый cap для PoC — не более 50 последних комментариев на заявку. Значение параметризуемо в конфигурации caller'а.
- **FR-009. Сохранение через SMP API.** Запись в pgvector — только через SMP API. Прямой JDBC запрещён.

## Нефункциональные требования

- **NFR-V2-001. PII — высокий риск.** `comment.text` содержит сообщения заявителей и операторов — PII-риск high. Отправка в YC FM разрешена: owner дал sign-off на все комментарии (Resolved OQ-V2-1 / OQ-ITSM-4, 2026-05-02). **Дополнительно:** создан OQ-V2-5 «PII-mask preprocessing для comment.text — defer to MVP» (см. ниже). Owner: Демьянов.
- **NFR-V2-002. ACL-инвариант.** Вектор комментария никогда не возвращается в поиске пользователю, у которого нет доступа к родительскому объекту (BR-001). Это инвариант: проверка ACL по parent_id, не по comment_id.
- **NFR-V2-003. Масштаб.** На llm2 — 31 844 комментариев issue. При full-vectorize: 31 844 × p50=53 ток. / 1 000 × 0,0101 ≈ 17 ₽. Аномальный объект с 8 248 комментариями × p95=2 432 ток. / 1 000 × 0,0101 ≈ 203 ₽ в одиночку — cap обязателен (FR-008).
- **NFR-V2-004. Preprocessing-версионирование.** `algorithm_version` входит в composite_hash. Смена алгоритма → полный пересчёт комментарных векторов.
- **NFR-V2-005. Изоляция по тенанту.** Векторы комментариев тенанта A не попадают в поиск тенанта B (аналогично UC-V1).

## User Journey

**Действующее лицо — scheduled job или event-driven caller.**

1. **Инициализация.** Caller запускает bulk-векторизацию комментариев (или обрабатывает отдельное событие «новый комментарий»).
2. **Фильтрация.** Caller запрашивает комментарии объекта из SMP API. Фильтрует по `comment.source.metaClass` (FR-006). Применяет cap (FR-008).
3. **Preprocessing.** Для каждого комментария: HTML-strip → нормализация по `nfr-preprocessing.md` → расчёт composite_hash (FR-007).
4. **Пропуск идемпотентных.** Если composite_hash совпадает с уже сохранённым — пропустить (FR-007).
5. **Векторизация.** Caller передаёт `{comment_id, parent_id, parent_meta_class, text}` в модуль. При тексте > лимита — chunking (FR-002).
6. **Сохранение.** Вектор сохраняется с `chunk_kind='related'`, `parent_id=issue.id`, `object_id=comment.id`.
7. **Удаление / обновление.** При удалении комментария — caller вызывает `deleteCommentVector(comment_id)`. При редактировании — dirty-флаг на comment_id → пересчёт (FR-004, FR-005).

**Альтернатива. Rate limit YC FM.** Retry с backoff (аналогично UC-V1 FR-012); исчерпание → `dirty=true`, следующий запуск.

## Бизнес-правила

- **BR-001. ACL по parent-объекту.** Вектор комментария в поиске возвращается только если у запрашивающего есть доступ к parent-объекту (`issue` / `problem`). Проверка — через SMP API по `parent_id`.
- **BR-002. Только user-комментарии.** System-комментарии (автоматически генерируемые SMP при смене статуса, SLA-событиях) из whitelist'а исключаются через `comment.source.excluded_meta_classes`. Точный список — OQ-V2-2.
- **BR-003. PII-default-deny.** `comment.text` не отправляется в YC FM без явного sign-off owner'а, зафиксированного в whitelist-конфигурации (ADR-005). До sign-off вся функциональность UC-V2 заблокирована на уровне конфигурации.
- **BR-004. Cap на количество комментариев — обязателен.** Caller не может передать более `comment.cap` комментариев на один вызов (default=50). Превышение → caller обрезает (не модуль).
- **BR-005. Версия модели обязательна.** Запись без `model_version` не создаётся (аналогично UC-V1 BR-003).

## Доменные события

- **CommentVectorized** (`comment_id`, `parent_id`, `parent_meta_class`, `chunk_total`, `model_version`) — вектор комментария сохранён.
- **CommentVectorFailed** (`comment_id`, `reason`, `correlationId`) — векторизация провалена.
- **CommentVectorDeleted** (`comment_id`) — вектор удалён по инициативе caller'а.
- **CommentVectorDirty** (`comment_id`) — комментарий отредактирован, вектор помечен на пересчёт.

## Acceptance Criteria

- [ ] **AC-001.** После векторизации комментария `C` заявки `I` в pgvector появляется запись с `object_id=C.id`, `parent_id=I.id`, `chunk_kind='related'`, непустым `model_version`.
- [ ] **AC-002.** Комментарий с `comment.text` > лимита токенов разбивается на чанки; в pgvector N строк с `chunk_index = 1,2,...` и корректным `chunk_total`.
- [ ] **AC-003.** Пользователь без доступа к заявке `I` не получает в UC-S2 комментарии этой заявки — даже если их векторы семантически близки (BR-001). Проверяется через тестовый аккаунт.
- [ ] **AC-004.** System-комментарий (метакласс из `excluded_meta_classes`) не попадает в векторизацию; smoke на конкретном system-комментарии из llm2.
- [ ] **AC-005.** После редактирования `comment.text` запись в pgvector получает `dirty=true` (или новый composite_hash); при следующем запуске джобы вектор пересчитывается.
- [ ] **AC-006.** После удаления комментария `C` строка(и) вектора `C` в pgvector удалены или помечены orphan; поиск UC-S2 не возвращает удалённый комментарий.
- [ ] **AC-007.** Передача идентичного `comment.text` дважды → второй вызов не делает YC FM-запрос (composite_hash совпадает).
- [ ] **AC-008.** Функциональность UC-V2 недоступна до выставления `comment.text.enabled=true` в whitelist-конфигурации (BR-003). Smoke: при `enabled=false` вызов возвращает ошибку «comment vectorization not enabled».
- [ ] **AC-009.** Caller передаёт более `cap` комментариев → модуль принимает только первые `cap` или возвращает ошибку «cap exceeded» (BR-004, FR-008).

## Бриф для SA

**Требование:** `content/30-requirements/functional/uc-v2-vectorize-comments.md`
**Фаза:** PoC

**Спроектировать:**
- DDL расширение (без новой таблицы): `chunk_kind='related'`, `parent_id UUID NULLABLE` — уже в схеме RES-009.2 §4. Реализация остального — после sign-off OQ-V2-1.
- ACL-механизм: фильтрация по parent_id через SMP kbAccessChecker (для KB-комментариев) или SMP-сессию (для issue/problem-комментариев).
- Lifecycle-контракт: как caller сообщает о deleted/edited комментарии — отдельный endpoint `DELETE /vector/comment/{id}` или через `dirty`-флаг.
- Cap-политика: как именно caller отбирает N комментариев (last N by dt, или top N by length, или configurable) — зафиксировать в API-контракте.

**Бизнес-правила для валидаций:** BR-001 (ACL по parent), BR-003 (PII-default-deny до sign-off), BR-004 (cap обязателен).

**AC для проверки архитектуры:** AC-003 (ACL-инвариант), AC-008 (feature-flag до sign-off), AC-009 (cap).

**Решения, требующие ADR:** OQ-COMMENT-DELETE (GC vs event), OQ-COMMENT-EDIT (dirty-механизм), cap-политика.
