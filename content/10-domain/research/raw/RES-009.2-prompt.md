§1. Сравнительная таблица стратегий A-E на 8 dimensions

Стратегии:
  A — single-vector (один объект = один composite-text = один embedding)
  B — multi-vector by content-type (subject vs description vs decisionReport — отдельные векторы, search через RRF/max-pool)
  C — chunked + parent-rollup (длинный текст → чанки фиксированной длины с overlap; rollup моделью при поиске)
  D — hybrid (issue → A на composite_extended; KB → C; одна таблица с chunk_index)
  E — per-related-vector (отдельный вектор на каждый связанный объект; для PoC — только в DDL под будущее)

Dimensions для каждой стратегии:
  1. Покрытие бизнес-кейсов из §1 RES-009.1 (12 пересечений UC × класс)
  2. Совместимость с лимитом токенов YC FM (после OQ-8 — точное число)
  3. YC FM cost при steady-state (новая заявка / новый комментарий / refresh KB)
  4. Storage schema: набор таблиц, FK, индексы (HNSW per таблица или общий)
  5. Search aggregation алгоритм + сложность (round-trips, post-processing)
  6. ACL-инвариант (только KB через kbAccesses; для chunked — где фильтровать)
  7. NFR-001 latency p95 ≤ 500 ms — оценка дополнительных SQL round-trips
  8. Сложность реализации в hexagonal layout (изменения в ports/adapters/core)

Формат: матрица 5×8 + per-cell обоснование (1-3 строки) + общий вывод по каждой стратегии.

§2. Search aggregation алгоритмы — детальный разбор

Для стратегий с multi-vector (C, D-KB, B):
  - Top-K чанков → GROUP BY parent_id → max similarity per parent → top-N parents
  - Oversample factor: сколько чанков top-K брать, чтобы получить N parents с высокой вероятностью
  - Reciprocal Rank Fusion (RRF) для multi-vector merging (B)
  - max-pool vs mean-pool vs first-chunk vs max-of-top-K (закрывает OQ-1)
  - Penalty/boost по полю (decisionReport > comments?) — для B
  
  На корпусе 113 KB-статей (медианный размер 6 428 chars / 1 836 ток., p95 91 049 chars / 26 014 ток.)
  оценить:
  - Сколько чанков на статью при размере 1 800 ток. без overlap, с 10 % overlap, с 20 % overlap
  - Total векторов в KB-таблице для каждой опции
  - Storage в МБ (256 dim × 4 байт × N векторов)
  - YC FM стоимость первичной векторизации (по yc-pricing.md: 0,0101 ₽/1k юнитов)

§3. Закрытие OQ-1 (rollup модель) — литературный обзор + recommendation

OQ-1: какая модель rollup эмбеддинга по чанкам — mean / max / first-chunk / max-of-top-K?

Действия:
  a. Через ctx7 / web-search — найти 2-3 релевантных RAG-исследования по rollup для русских текстов или multilingual
  b. Сравнить характеристики:
     - mean: усредняет, теряет острые сигналы, лучше для коротких запросов
     - max-of-top-K: сохраняет самый похожий чанк, лучше для точечных query
     - first-chunk: для KB-статей с TL;DR в начале
     - hierarchical (summary-vector + chunks): два запроса, лучшее качество, дороже
  c. Дать рекомендацию для волны 3 с обоснованием
  d. Зафиксировать что финальный выбор — после offline-eval на ground truth (DEV-033/034)

§4. Закрытие OQ-2/OQ-3 (chunk overlap + chunk size)

OQ-2: chunk overlap 0 / 10 % / 20 %?
OQ-3: фиксированный (1 800 ток.) / adaptive (по абзацам) / sentence-aware?

Действия:
  a. Стандарты RAG (LangChain RecursiveCharacterTextSplitter, LlamaIndex SentenceSplitter)
  b. Trade-off: больше overlap = больше vectors = больше cost (linear)
  c. Для KB.content (HTML richtext) — нормализация перед чанкингом обязательна
  d. Рекомендация для PoC: фиксированный размер с tokenizer-aware границей
     (т.е. не разрывать слова посередине), overlap 10-15 %
  e. Решить вопрос: что делать с очень длинными отдельными "абзацами" 
     (KB max = 75 010 токенов — это явно один большой HTML-блок)

§5. Закрытие OQ-4 (ACL при multi-chunk)

OQ-4: где фильтровать ACL для KB при chunked-стратегии?

Контекст: на llm2 ACL у KB через kbAccesses (per-article). У issue/problem — управляется
SMP-сессией, не атрибутами. Значит, per-chunk ACL нужен ТОЛЬКО для KB.

Алгоритм поиска для D-strategy на KB:
  1. SELECT chunk_id, parent_id, vector <-> :query AS dist FROM vectors WHERE meta_class='knowledgeBase$article' ORDER BY dist LIMIT (K × oversample)
  2. GROUP BY parent_id → min(dist) per parent
  3. SELECT top-N parents
  4. ACL-фильтр на стороне SMP API через KbAccessChecker (UC2 BR-002)
  5. Если после фильтра < N — повторить с большим oversample (или принять short result)

  - Оценку доп. round-trips
  - Эффект на NFR-001 (p95 ≤ 500 ms)

§6. Закрытие OQ-5 (source_attr колонка) и OQ-9 (DDL под будущую E)

OQ-5: нужна ли source_attr колонка в PoC?
OQ-9: как поддержать E (per-comment-vector) в DDL без реализации?

Подход:
  - Базовая таблица должна иметь `chunk_kind` (enum) или конвенцию через chunk_index
  - Варианты конвенции:
    1. `parent_id` UUID NULLABLE: для chunks parent_id = object_id; для related (E) — parent_id = id связанного объекта
    2. `source_attr` TEXT NULLABLE: имя SMP-атрибута, из которого взят текст (для B и E)
    3. `chunk_kind` TEXT: 'object' (single), 'chunk' (часть длинного), 'related' (связанный объект)
  
  Сравнить с конвенцией pgvector RAG-туториалов (Supabase/Vespa/Weaviate) — что 
  считается стандартом.
  
  Рекомендация для PoC DDL:
    - parent_id UUID NULLABLE (стартует NULL для single-vector A)
    - chunk_index SMALLINT NOT NULL DEFAULT 0
    - chunk_total SMALLINT NOT NULL DEFAULT 1
    - source_attr VARCHAR(64) NULLABLE
    - chunk_kind: использовать конвенцию или enum?

§7. Закрытие OQ-6 (детерминированность chunking)

OQ-6: как гарантировать детерминированность chunk_index при ре-векторизации?

Контекст: composite_hash должен быть стабилен → если каждый refresh даёт разное
число чанков, все чанки помечаются dirty.

Решение:
  - Алгоритм чанкинга — детерминированный (фиксированный seed для tokenizer-aware split)
  - composite_hash = sha256(text + model_version + whitelist_version + chunk_size + chunk_overlap + algorithm_version)
  - chunk_index = порядковый номер от начала текста
  - Если меняется algorithm_version (smoke в Dev) — миграция через ADR-007

Зафиксировать в §7 алгоритм с псевдо-кодом.

§8. Закрытие OQ-7 (summary-row vs on-the-fly rollup)

OQ-7: хранить отдельный summary-вектор (chunk_index=0=summary) или считать на лету?

Trade-off:
  - Summary-row: +1 строка/объект (+113 строк для KB на llm2), +1 embedding-call при векторизации,
    но search быстрее (один query + top-K, не нужен GROUP BY)
  - On-the-fly: меньше storage, но GROUP BY parent_id по chunked-таблице на каждый search
  
На корпусе 113 KB:
  - Summary-row: 113 доп. векторов × 256 dim × 4 байт = 116 КБ — **тривиально**
  - YC FM cost summary: 113 × ~200 ток. (compressed summary) × 0,0101/1k = ~0,23 ₽ — **тривиально**

Рекомендация: **summary-row для KB** — простота поиска и tiny overhead перевешивает.
Для issue (single-vector A) — chunk_index=0 уже и есть summary; not applicable.

§9. Закрытие OQ-8 (точный лимит YC FM text-search-doc)

OQ-8: 2 048 или 8 000 токенов?

`https://llm.api.cloud.yandex.net/foundationModels/v1/textEmbedding`,

Если возвращает 400 / truncation warning — лимит ниже, fallback к 2 048.

Креды у owner'а в `.secrets/yc-api-key.json`. Researcher должен попросить owner'а
запустить curl и прислать ответ — не пытаться доставать секреты сам.

§10. Закрытие OQ-10 (truncation policy для редких длинных issue)

OQ-10: что делать с 0,4 % issue (25 объектов из 6 223), у которых composite_extended
превышает лимит?

Варианты:
  a. Caller обрезает до 2 000 ток. перед отправкой (KISS, документируем в API контракте)
  b. Модуль возвращает ошибку 413 ContentTooLarge → caller повторяет с C (chunked)
  c. Модуль автоматически переключается на C для overflow

Для PoC — рекомендация (a): простейшая, явная, caller знает что делает.
Для MVP — пересмотр на (c) для UX.

median 22 токена composite. Это критически мало для realistic UC2/UC3.

В §12 артефакта зафиксировать:
  - Numerical evidence: median, p50, p95 composite_poc vs composite_extended
  - Quality risk: вероятность Recall@10 ≥ 0,7 на median 22 ток. composite — 
    близка к нулю
  - Рекомендация для BA: ускорить sign-off на medium-PII атрибуты 
    (description, decisionReport, feedback) до старта PoC iter 1, не после
  - Альтернатива: PoC iter 1 идёт на composite_extended с whitelist sign-off,
    PoC iter 0 (smoke) — на PoC-whitelist для проверки end-to-end pipeline
