# Сквозные нефункциональные требования pg_vector_service

> **Diff BA-002 (2026-05-01):** добавлены NFR-070..NFR-075 (ACL-наследование комментариев, preprocessing-версионирование, UC-S2 latency бюджет, детерминированность, comment-векторы). Ссылки на UC1/UC2/UC3 заменены на UC-V*/UC-S*/UC-C*. Новый документ preprocessing-политики: `content/30-requirements/non-functional/nfr-preprocessing.md`.

Требования, применимые ко всему модулю независимо от конкретного use case'а. UC-специфичные NFR (например, p95 поиска для UC-S1 / UC-S2 или throughput batch-векторизации для UC-V1) живут в самих UC-артефактах в `content/30-requirements/functional/` и при необходимости ссылаются на этот документ.

Контекст-источники:
- `CLAUDE.md` — red lines, целевые объёмы (медиана 100k–300k, диапазон 10k–10M), фиксированный стек.
- `content/00-project/stakeholders.md` — RACI, gate-keeper'ы (Сахабетдинов / Сазонова / Киселёва).
- Research: `smp-metamodel.md` (PII-категоризация атрибутов, baseline whitelist), `yc-foundation-models.md` (auth, лимиты, тарификация), `pgvector-indexes.md` (индексы и память), `smp-scheduled-jobs.md` (модель джобы), `reference-project-notes.md` (паттерны эталона).

## 1. Безопасность и privacy

- **NFR-001 (Whitelist текстовых атрибутов, default-deny):** Модуль отправляет в Yandex Cloud Foundation Models только текст из явно перечисленного per-class whitelist'а атрибутов. Любой атрибут, отсутствующий в whitelist'е, игнорируется на этапе сборки композитного текста. Изменение whitelist'а — отдельная конфигурация, версионируется вместе с модулем.
  - Обоснование: red line из `CLAUDE.md` (риск утечки PII в облачную модель). Baseline whitelist — таблица «Сводный whitelist кандидатов» в `smp-metamodel.md`.
  - Решение по формату конфигурации whitelist'а закрепится в **ADR-config-whitelist**.

- **NFR-002 (PII-категоризация атрибутов):** Каждый атрибут в whitelist'е помечен уровнем PII-риска (low / medium / high) согласно классификации в `smp-metamodel.md`. Атрибуты уровня high (`description`, `lastComment`, `feedback` для `issue`) на PoC-итерации 1 **запрещены** к отправке без явного разрешения owner'а и фиксации этого исключения в whitelist-конфиге.
  - Обоснование: запрос Демьянова на PII-аудит до первой отправки данных в облако (`CLAUDE.md`, фаза 1 BA).
  - Решение по режиму обработки medium-PII (mask vs allow vs reject) закрепится в **ADR-pii-masking**.

- **NFR-003 (Аудит-логирование вызовов YC FM):** Каждый запрос к Yandex Cloud Foundation Models порождает структурированную запись аудит-лога с полями: timestamp, correlationId, FQN объекта-источника, идентификатор объекта (UUID/number), список использованных атрибутов (имена, не значения), длина композитного текста в символах и токенах (если доступно), `modelUri`, HTTP-status ответа, длительность вызова. Сами тексты и численные эмбеддинги в аудит-лог **не пишутся**.
  - Обоснование: возможность ретроспективно ответить на вопрос «что и куда было отправлено по объекту X» без сохранения контента.
  - **Resolved OQ-7 (2026-05-02):** Аудит-лог хранится в системном `logger.info` (не отдельный FQN-объект). Owner: Демьянов. Закрепится в **ADR-audit-log**.

- **NFR-004 (Запрет логирования сырых текстов и эмбеддингов):** В обычные (не-аудит) логи модуля запрещено писать содержимое атрибутов из whitelist'а (`description`, `lastComment` и т. п.) и численные значения эмбеддингов целиком. При ошибках допускается логировать только метаданные (длина, hash префикса, FQN) + correlationId.
  - Обоснование: red line из `CLAUDE.md` («error responses наружу — без stack traces; stack → в лог с correlationId»). Расширяется на текстовый контент.

- **NFR-005 (Ротация ключей YC IAM):** Ключ авторизованного сервисного аккаунта YC (источник IAM-токенов) хранится как secret SMP-инстанса. Процедура ротации ключа без перезапуска модуля поддерживается на уровне runbook DevOps. IAM-токен в памяти модуля кешируется на срок ≤ 11 часов (refresh за час до истечения, см. `yc-foundation-models.md` § 5).
  - Обоснование: рекомендация YC по сроку жизни IAM-токена (12 часов max) + общая практика secret-management.
  - **Resolved OQ-10 (2026-05-02):** Вариант авторизации — IAM-токен с JWT-обменом. Статический Api-Key не используется. Owner: Демьянов. Решение закрепится в **ADR-yc-auth**.

- **NFR-006 (Запрет JDBC-доступа к защищённой БД):** Модуль не открывает прямые JDBC-соединения к PostgreSQL стенда. Любые операции с векторной таблицей (чтение, вставка, поиск, индексация) выполняются через SMP API: HQL `api.db.query` для read-only, REST `/edit`, `/create`, `/find` или script-методы модуля для записи.
  - Обоснование: red line из `CLAUDE.md` («доступ к БД — только через SMP API»); БД физически защищена от прямого подключения.
  - Решение по способу записи в pgvector-таблицу через SMP API (FQN-объект-обёртка / стораджный adapter / иное) закрепится в **ADR-vector-storage**.

## 2. Производительность

- **NFR-010 (Throughput векторизации — задаётся для джобы):** Целевой throughput batch-векторизации (объектов в час) задаётся в UC-V1 «scheduled-векторизация» с учётом фактической квоты YC FM RPS (40 RPS, OQ-4 Resolved) и доступной параллельности SMP scheduler'а.
  - **Resolved OQ-2 (2026-05-02):** Для PoC — пересчёт по запросу, ограничений по окну нет. Для Production / Pilot+: полный пересчёт укладывается в 6-часовое ночное окно при медиане 100k–300k объектов. Owner: Демьянов.
  - Обоснование: целевые объёмы 100k–10M (`CLAUDE.md`), при 40 RPS YC FM полный пересчёт 300k объектов ≈ 2 ч 5 мин чистого embedding-времени плюс DB-write.
  - Источник цифр: RES-002 (квота YC FM) + RES-003 (бюджет) + первые smoke-замеры на `llm2`.

- **NFR-011 (p95 latency similarity-поиска):** Задаётся в UC-2 «найди похожие». Здесь фиксируем кросс-uc инвариант: индекс pgvector выбран и параметризован так, чтобы при медиане 100k–300k векторов запрос top-K (K ≤ 50) с recall ≥ 0.95 укладывался в **бюджет, согласованный в UC-2**. Численный бюджет SLA на PoC **не предзадан** (`CLAUDE.md`: «SLA анализируем по итогам PoC, не предзадаём»).
  - Обоснование: предотвратить рассинхрон NFR через UC-2 (бизнес-SLA) и архитектурный выбор индекса.
  - Решение по типу индекса (HNSW vs IVFFlat) и параметрам (`m`, `ef_construction`, `ef_search`) закрепится в **ADR-pgvector-index** (см. `pgvector-indexes.md`).

- **NFR-012 (Память pgvector-индекса в пределах ресурсов `llm2`):** Размер pgvector-таблицы и сопутствующего индекса при текущем целевом объёме (медиана + headroom 2×) укладывается в свободные ресурсы стенда `llm2` без деградации других сервисов SMP.
  - **Resolved OQ-1 (2026-05-02):** Хранение — **на диске** (disk-resident). PostgreSQL-сервер общий на несколько клиентов — память не перегружать. Owner: Демьянов.
  - **Acceptance criterion (добавлен addendum BA-004.1):** Индекс не требует pinned-memory; работает при `shared_buffers` уровне общего стенда. Bulk-индексирование выполняется батчами с контролем memory pressure.
  - Обоснование: `pgvector-indexes.md` § 3 — HNSW при 1M векторов требует 8–32 GB `maintenance_work_mem` для построения; стенд `llm2` shared с другими модулями.
  - Решение по типу индекса: ADR-pgvector-index должен предпочитать disk-resident конфигурацию — IVFFlat (по умолчанию disk-friendly) или HNSW с консервативными параметрами (`m=16`, `ef_construction=64`, минимальный memory footprint). Решение закрепится в **ADR-pgvector-index**.

- **NFR-013 (Чанкинг длинных текстов):** Композитный текст объекта, превышающий лимит токенов выбранной embedding-модели YC FM, разбивается на чанки до отправки в облако. Способ агрегирования эмбеддингов чанков обратно в один вектор объекта (mean-pooling / first-chunk / per-chunk хранение) фиксируется в ADR.
  - Обоснование: `yc-foundation-models.md` § 3 — большинство SMP-объектов превышают лимит ~2048 токенов; baseline-модуль уже делает чанкинг.
  - Решение закрепится в **ADR-text-chunking**.

## 3. Надёжность

- **NFR-020 (Идемпотентность scheduled-джобы):** Повторный запуск джобы векторизации не порождает новых вызовов YC FM для объектов, чей контент не менялся с последней успешной векторизации. Признак «не менялся» определяется по детерминированному ключу (хеш композитного текста + версия модели + версия whitelist'а).
  - Обоснование: бюджет YC FM (`CLAUDE.md`) не позволяет пересчитывать всю базу при каждом запуске; baseline-модуль уже использует UNIQUE `(ext_id, entity, number)`.
  - Решение по составу ключа идемпотентности и месту его хранения закрепится в **ADR-vector-storage**.

- **NFR-021 (Retry для transient-ошибок YC FM и rate-limit):** При получении HTTP 429 (rate limit), 5xx или сетевых таймаутов от YC FM модуль выполняет ограниченное число повторов с экспоненциальной задержкой. На исчерпании retry — объект помечается как «не векторизован в этом запуске» и обрабатывается следующим запуском джобы; джоба не падает целиком.
  - **Resolved OQ-4 (2026-05-02):** RPS-квота YC FM — **до 40 RPS** (не больше). Owner: Демьянов.
  - **Acceptance criterion (добавлен addendum BA-004.1):** UC-V1/UC-V2 не превышают 40 RPS к YC FM Embeddings API. В архитектуре — rate-limiter (Bucket4j или Resilience4j RateLimiter, 40 permits/sec) в YC FM-адаптере.
  - Bulk-init расчёт ETA: 300k объектов / 40 RPS ≈ 2 ч 5 мин чистого embedding-времени плюс DB-write.
  - Обоснование: RPS-квота YC FM зафиксирована Демьяновым; сетевая граница `llm2` ↔ `*.api.cloud.yandex.net` нестабильна по умолчанию.
  - Решение по конкретным параметрам (число попыток, верхняя граница backoff, jitter, rate-limiter реализация) закрепится в **ADR-yc-retry**.

- **NFR-022 (Восстановление chunked-job с прерванной точки):** Если scheduled-джоба прерывается (Thread Death через `api.scheduler.interruptJob`, ошибка SMP, рестарт инстанса), следующий запуск возобновляет работу с непросчитанных объектов, не пересчитывая уже записанные векторы текущей версии модели/whitelist'а.
  - Обоснование: `smp-scheduled-jobs.md` § 1 — джоба может быть прервана из UI; объёмы 100k+ не позволяют рестартовать с нуля.
  - Решение по механизму прогресс-маркера (state в FQN-объекте / `subject` scheduledTask / отдельная таблица) закрепится в **ADR-job-state**.

- **NFR-023 (Транзакционность батча):** Каждый батч векторизации внутри джобы оборачивается в `api.tx.call()` и фиксируется отдельно. Падение батча не откатывает уже зафиксированные предыдущие батчи.
  - Обоснование: паттерн SMP scheduled jobs (`smp-scheduled-jobs.md` § 1, рекомендация резюме); защита от потери прогресса при ошибке в N+1-м объекте.

## 4. Совместимость и эволюция

- **NFR-030 (Версионирование embedding-модели):** Каждая запись в pgvector-таблице помечена идентификатором модели и её версии (полный `modelUri` + дата pin'а). При смене модели или её размерности новые векторы пишутся в **новую** таблицу/колонку, старые остаются доступны до миграции запросов на новую модель. Одновременная работа двух моделей на одном корпусе — допустимый временный режим, оформляется в runbook миграции.
  - Обоснование: red line из `CLAUDE.md` («при смене модели — миграция векторной таблицы, новый ADR со ссылкой на superseded»). Размерности моделей `text-search-doc` и `text-search-query` несовместимы между разными моделями.
  - Решение по схеме «как именно версионировать» (отдельная таблица / отдельная колонка / отдельный namespace) закрепится в **ADR-vector-storage** + **ADR-embedding-model**.

- **NFR-031 (SemVer модуля):** Версия модуля (`pom.xml`) подчиняется SemVer (MAJOR.MINOR.PATCH). MAJOR — обратно-несовместимое изменение SPI или схемы векторной таблицы; MINOR — новые возможности без слома; PATCH — багфиксы. Паттерн версионирования заимствуется из эталона `naumen-smp-mcp` (см. ADR-013 эталона).
  - Обоснование: `reference-project-notes.md` § 1 — эталон уже использует SemVer + API SMP версия; нужно для совместимости JAR с разными SMP-инстансами.
  - Решение по матрице совместимости (какие SMP-версии поддерживает MAJOR X) закрепится в **ADR-platform-versioning**.

- **NFR-032 (Версионирование whitelist'а атрибутов):** Изменения per-class whitelist'а версионируются. При расширении whitelist'а (добавление атрибута) векторы объектов, чей композитный текст изменился из-за нового атрибута, помечаются как «требуют пересчёта»; джоба пересчитывает их инкрементально.
  - Обоснование: расширение whitelist'а — это фактически смена входа модели; иначе старые и новые векторы несравнимы между собой.
  - Связь с NFR-020 (идемпотентность): версия whitelist'а — часть ключа идемпотентности.

## 5. Архитектурные red lines (фиксируем для SA)

> Эти пункты дублируют red lines из `CLAUDE.md` в формате NFR — чтобы при проектировании в `/sa` не было «отклонения по умолчанию».

- **NFR-040 (БД только через SMP API):** Дублирует NFR-006 в архитектурном разрезе. Проектное решение SA не должно вводить компонент с прямым JDBC-соединением к БД стенда. Любые «оптимизирующие» обходы (например, прямой connection pool к pgvector) — отклоняются.

- **NFR-041 (Только whitelist'ные тексты в YC FM):** Дублирует NFR-001. Архитектура должна гарантировать, что точка выхода в YC FM (адаптер) принимает на вход только результат сборки композитного текста из whitelist'а, и не имеет «прямого» доступа к произвольным атрибутам объекта.

- **NFR-042 (Размерность и `modelUri` зафиксированы в ADR):** Размерность вектора и полный `modelUri` (включая pinned версию) — параметры, фиксируемые в ADR. Изменение любого из них — новый ADR с пометкой `supersedes` на старый и сценарий миграции (NFR-030).

- **NFR-043 (HQL только параметризованный):** Дублирует red line `CLAUDE.md`. В коде модуля все HQL-запросы используют `setParameter(...)`. Интерполяция строк в HQL — запрещена архитектурно (CodeNarc-правило, см. эталон).

- **NFR-044 (Изоляция `@InjectApi`):** Аннотация `@InjectApi` (доступ к SMP API) допустима только в `adapters/smp/` и `config/`. Доменное ядро (`core/`) и SPI (`spi/`) не имеют зависимости от SMP runtime — тестируются без SMP-контекста (паттерн hexagonal из `reference-project-notes.md` § 3).

## 6. Наблюдаемость

- **NFR-050 (Метрики модуля):** Модуль экспортирует метрики:
  - throughput векторизации (объектов/мин по FQN);
  - success-rate вызовов YC FM (success / 4xx / 5xx / network-error);
  - размер pgvector-таблицы (число строк) и индекса (бытовой запрос к pg_class — через SMP API);
  - частота similarity-запросов (вызовов в минуту, разрезы по FQN);
  - длительность p50/p95/p99 ключевых операций (embedding-вызов, similarity-search).
  - Обоснование: без метрик невозможно валидировать SLA-гипотезы по итогам PoC (`CLAUDE.md`: «SLA анализируем по итогам PoC»).
  - **Resolved OQ-3 (2026-05-02):** Стек метрик — **внешний Prometheus + Grafana** настроен и доступен на `llm2`. Owner: Демьянов.
  - Метрики экспортируются через Prometheus-endpoint (Micrometer / Prometheus Java client из JAR-модуля). Логи — через стандартный SMP-logger (`logger.info` для аудита YC FM, см. NFR-003). Решение закрепится в **ADR-observability**.

- **NFR-051 (Структурированные логи):** Все логи модуля — структурированные (JSON или KV-формат, на усмотрение SA с учётом возможностей SMP-логгера). Каждая запись содержит correlationId — для трассировки от вызывающего сценария SMP до вызова YC FM и обратно.
  - Обоснование: для разбора инцидентов на больших объёмах (`smp-scheduled-jobs.md` § 1 рекомендация); паттерн эталона.

- **NFR-052 (Корректное логирование исключений):** В каждом tool/handler-методе модуля — `try/catch (Throwable)`, `logger.error(msg, e)`, повторный `throw e`. SMP-инстанс не логирует uncaught exceptions автоматически (red line `CLAUDE.md`).
  - Обоснование: red line из `CLAUDE.md`, ссылка на эталон.

## 7. Бюджет и стоимость (за рамки SLA)

- **NFR-060 (Расход YC FM мониторится):** Модуль публикует метрику расхода YC FM (количество вызовов, входные токены — если YC API отдаёт их в ответе, иначе оценочно по длине запроса). Расход агрегируется суточно с возможностью разреза по FQN и типу операции (doc-векторизация / query-векторизация).
  - Обоснование: бюджет YC FM — открытый вопрос (`CLAUDE.md`, RES-003); без метрики его невозможно валидировать на проде.

- **NFR-061 (Алёрт при превышении дневного лимита):** При достижении настроенного дневного лимита расхода (в токенах или вызовах) модуль:
  1) отправляет алёрт по DevOps-каналу,
  2) переходит в degrade-режим (приоритет обработки query-векторизации над doc-векторизацией; пауза scheduled-джобы до начала следующих суток).
  - Обоснование: защита от runaway-расхода (например, после ошибочного сброса prog-маркера джобы).
  - **Resolved OQ-6 (2026-05-02):** Дневной лимит = 1 000 ₽/сутки. Owner: Демьянов. Создан OQ-FUTURE-1 для unit economics расчёта (см. § 8).

- **NFR-062 (Лимит на one-shot batch):** Принудительный batch-пересчёт всей таблицы (через явную команду оператора) ограничен сверху по числу объектов и/или токенов в одном запуске. Превышение — требует подтверждения оператором с указанием причины (свободное поле, пишется в аудит-лог).
  - Обоснование: защита от ошибочного запуска полного пересчёта при объёмах 1M+ (десятки тысяч ₽ за один клик; `yc-foundation-models.md` § 4).
  - Решение закрепится в **ADR-batch-control**.

## 8b. Дополнительные сквозные NFR (BA-002, 2026-05-01)

> Добавлены по итогам расширения каталога UC (BA-002): UC-V2 (comment-векторы), UC-S2 (поиск по comment-векторам), preprocessing-политика (Mixed strategy), RES-009.2 OQ-6 (детерминированность).

- **NFR-070 (ACL-наследование комментариев).** Доступ к результатам поиска/кластеризации по comment-векторам (UC-S2, UC-C2) определяется правами **родительского объекта** (`issue`, `problem`, `knowledgeBase$article`), а не самого комментария. Пользователь видит комментарий в результатах поиска только если у него есть доступ к родительскому объекту. Проверка выполняется постфильтрацией в Java-слое по parent_id до возврата результата клиенту.
  - Обоснование: в SMP комментарии не имеют собственного ACL-объекта; права на просмотр комментария равны правам на объект-родитель.
  - Решение по реализации ACL-фильтра (WHERE IN parent_ids / post-filter loop / SMP ACL API) закрепится в **ADR-comment-acl**.

- **NFR-071 (Preprocessing-версионирование в composite_hash).** Алгоритм нормализации текста (`algorithm_version`) входит в ключ идемпотентности:
  ```
  composite_hash = sha256(
      normalized_text + "|" + model_version + "|" + whitelist_version
      + "|" + chunk_size + "|" + overlap + "|" + algorithm_version
  )
  ```
  При смене `algorithm_version` все ранее сохранённые хеши инвалидируются → все объекты затронутых классов получают `dirty=true` → джоба UC-V1/UC-V2 пересчитывает векторы. Текущая версия для PoC: `v1.0-mixed`.
  - Обоснование: без версионирования preprocessing старые и новые векторы несравнимы (разные тексты на вход модели); детально обосновано в `content/30-requirements/non-functional/nfr-preprocessing.md` § «Версионирование preprocessing».
  - Связь: NFR-020 (идемпотентность), NFR-032 (версионирование whitelist'а), UC-V1 FR-008, UC-V2 FR-006.

- **NFR-072 (Отдельный latency-бюджет для UC-S2).** NFR-011 (p95 latency similarity-поиска) устанавливает общий кросс-UC инвариант. Для UC-S2 (поиск по comment-векторам с GROUP BY parent_id) устанавливается **отдельный расширенный бюджет**: p95 ≤ **1 000 ms** при mediane 100k–300k comment-векторов и K_oversample ≤ 50. Обоснование: GROUP BY + MIN(dist) агрегация добавляет ~2× overhead vs прямой KNN-поиск UC-S1.
  - Связь: UC-S2 NFR-S2-001, ADR-pgvector-index (нужно проверить ef_search для comment-таблицы).
  - Численный бюджет подтверждается на smoke-тестах на `llm2`.

- **NFR-073 (Детерминированность preprocessing — инвариант системы).** Для фиксированного `algorithm_version` и фиксированного входного текста preprocessing **всегда** возвращает идентичный результат. Нарушение детерминированности является дефектом критической степени: приводит к тому, что одинаковые объекты получают разные `composite_hash` в разных запусках, что ломает идемпотентность UC-V1/UC-V2 (NFR-020).
  - Запрещённые источники недетерминированности: случайность в UUID/timestamp внутри preprocessing, language-locale-зависимые правила нормализации, stateful side effects библиотеки (flexmark instance должен быть immutable/stateless или создаваться per-call).
  - Источник: RES-009.2 OQ-6 (детерминированность hash) — закрывается этим NFR совместно с `nfr-preprocessing.md` NFR-PRE-001.
  - Связь: NFR-PRE-001 в `content/30-requirements/non-functional/nfr-preprocessing.md`.

- **NFR-074 (Комментарии: cap-ограничение на объект).** Для каждого родительского объекта число comment-векторов, создаваемых UC-V2, ограничено сверху параметром `comment_cap` (default=50). Это защищает от аномальных объектов (на `llm2` выявлен объект с 8 248 комментариями, см. RES-009.1/2). При достижении cap: UC-V2 обрабатывает последние N комментариев по `creationDate DESC`; превышение cap фиксируется в аудит-лог с предупреждением.
  - Обоснование: без cap один объект генерирует 8 248 вызовов YC FM (≈ 8,3 ₽ только на этот объект при среднем размере комментария) и потребляет непропорциональную долю квоты RPS.
  - Связь: UC-V2 FR-008, OQ-V2-2.

- **NFR-075 (Системные комментарии — исключение из векторизации).** Комментарии с `meta_class` в списке `excluded_comment_meta_classes` (конфигурируемый, default=`['commentprivate', 'commentaudit']` или аналог) **не векторизуются** в UC-V2. Системные / аудитные комментарии не несут семантической нагрузки и засоряют пространство векторов.
  - **BA-003-m2:** данный NFR **неполон** до закрытия OQ-V2-2 (точный список `excluded_comment_meta_classes` на стенде `llm2`). До закрытия OQ-V2-2: (a) NFR-075 не может быть проверен через AC, (b) UC-S2 Variant B (фильтрация по comment-type) не реализуем. Приоритизировать через MCP `metamodel_export_class comment` + анализ подклассов `comment` или запрос к Сахабетдинову. Блокер для UC-V2 реализации.
  - Конкретные meta_class системных комментариев на `llm2` — открытый вопрос OQ-V2-2 в UC-V2.
  - Связь: UC-V2 FR-007 (фильтрация системных комментариев), UC-S2 OQ-S2-5.

## 9. Бриф для SA

**Что спроектировать (на основе этих NFR):**

- **Whitelist-конфигурация (NFR-001/002/032):** формат хранения per-class whitelist'а, версионирование, способ загрузки в модуль (resource в JAR / SMP-объект / properties-файл), интеграция с PII-уровнями (low/medium/high).
- **Адаптер YC FM (NFR-003/005/021/060):** точка выхода в облако с обязательными хуками: аудит-лог, retry, IAM-токен-кеш, метрики расхода. Контракт SPI — что именно дёргается из core.
- **Storage-адаптер pgvector (NFR-006/012/030):** работа с pgvector **только через SMP API**; схема таблицы (с учётом версионирования модели и whitelist'а из NFR-020/030/032); план миграции при смене модели.
- **Scheduled-джоба (NFR-010/020/021/022/023):** механизм идемпотентности (хеш композитного текста + версия модели + версия whitelist'а + algorithm_version, NFR-071), state прогресса, обёртка `api.tx.call()`, обработка interrupt.
- **Чанкинг (NFR-013):** способ разбиения композитного текста и агрегирования эмбеддингов чанков; версионируется ли стратегия чанкинга наравне с моделью.
- **Preprocessing-компонент (NFR-071/073):** реализация Mixed strategy (`nfr-preprocessing.md`); детерминированность; algorithm_version в composite_hash; тестируемость без SMP.
- **ACL-фильтр comment-векторов (NFR-070):** постфильтрация по parent_id; реализация без прямого ACL-API комментария.
- **Versioning (NFR-031):** SemVer-схема модуля по образцу эталона; политика breaking changes для SPI.
- **Observability (NFR-050/051/052):** реестр метрик и формат логов; correlationId.

**Бизнес-правила для валидаций (общие, без привязки к UC):**

- BR-cross-1: Текст в whitelist'е уровня high не уходит в YC FM без явного разрешения owner'а в whitelist-конфиге.
- BR-cross-2: Запись в pgvector-таблицу без идентификатора модели/версии — запрещена.
- BR-cross-3: Любое изменение whitelist'а инвалидирует затронутые векторы (`status = 'stale'`).
- BR-cross-4: HQL-запросы — только параметризованные.
- BR-cross-5: comment-вектор в результатах поиска/кластеризации виден пользователю только при наличии прав на родительский объект (ACL-наследование, NFR-070).
- BR-cross-6: algorithm_version входит в composite_hash; смена алгоритма нормализации инвалидирует все хеши и вызывает full-rescan (NFR-071).
- BR-cross-7: preprocessing-компонент детерминирован и idempotent для фиксированного algorithm_version (NFR-073).
